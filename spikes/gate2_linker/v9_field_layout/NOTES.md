# V9 类字段布局变更 —— 第 1 层（静态完备性）

**问题**：给类增删字段会改变对象内存布局。要验证：linker 能否**完备**识别所有访问该
类字段的函数（都转解释、用新布局），不漏一个（漏一个 = 基线机器码用旧偏移访问新布局
对象 = 内存错乱）；且不误伤无关函数。

跑：`DART_SDK_SRC=/root/dart/sdk ./run_v9_static.sh`
用例：`Point{x,y}` →(patch)→ `Point{x,z,y}`（`z` 插在中间且被读）。`sumXY`/`bumpY`/
`unrelated` 源码在两版**完全相同**。

## 结论 1：核心机制正确（受控函数）

抽查三个唯一命名的受控函数（`compare_fn.py`，窗口已修到 0x400）：

| 函数 | 源码 | 结果 | 说明 |
|---|---|---|---|
| `sumXY(p)=>p.x+p.y` | 未改 | byte-changed ✓ | 读 y 的偏移 `0xf→0x17`（`48 8b 57 0f`→`...17`） |
| `bumpY(p,d){p.y+=d}` | 未改 | byte-changed ✓ | 写 y 的偏移 `0xf→0x17` |
| `unrelated(n)=>n*2+1` | 未改 | **equivalent** ✓ | 不碰 Point，纯算术，位置无关，字节不变 |

→ **字段布局变更后，访问该字段的函数（源码没改也一样）因偏移立即数变化而字节不等价，
被完备捕获；不碰该类的纯函数正确幸免。** 这是 V9 完备性的核心，成立。P1 已证"访问者
字节必变"，这里在真实多函数程序里复现。

## 结论 2（关键、也是 Gate 2 最深的发现）：真实闭包极小，但漂移噪音淹没它

diff linker 全量跑（optimistic 模式）却报 **byte-changed 1184 个（41%）、闭包 62.6%**。
逐个查那些"无辜"的 runtime 函数（如 `DateTime.toString`，逻辑一字未改），差异只有两类：

1. **代码段布局平移** —— `call <stub AllocateArray>` 目标 `14d318→14d36c`：补丁新增了
   函数/常量，把 stub 整体后移，而调用方没动，二者相对距离变 → pc-relative rel32 变。
2. **对象池 slot 漂移** —— `mov 0x6dc7(%r15)→mov 0x6dcf(%r15)`（+8）、`0x6dcf→0x6dd7`：
   补丁新增池常量（`z` 字段、`'z='` 字符串）把后续 slot 整体推后一格，所有引用池的
   函数偏移立即数随之变。

→ 这 1184 个**几乎全是漂移噪音，不是真逻辑变化**。真实闭包（真访问 Point 的函数 +
其传递闭包）只有个位数（对照 P2：无漂移的纯改动闭包=3）。

## 这对 Gate 2 可行性的精确刻画

- **难点不是"闭包爆炸"**（真实闭包极小、有界），**而是"漂移噪音"**：补丁引入任何新
  常量 / 新函数 → 对象池 slot 全局漂移 + 代码段布局平移 → 几乎所有引用池或调用 stub
  的函数字节变化 → naive 字节比对被淹没（假闭包 62.6%）。
- 因此 linker 的"逐字节等价判定"**不能真的逐字节**，必须先**归一化**：pc-relative
  call 目标归一成"目标符号"（消代码段平移）、对象池 slot 引用归一成"池里哪个常量"
  （消 slot 漂移），归一化之后再比，才能把"真逻辑变化"从漂移噪音里分离出来。
- 这**印证并扩展**了 SPEC §4.3：不只 **cid** 要稳定化，**对象池 slot 分配 + 代码段
  函数布局**也要稳定化 / 归一化。**对齐（CanonicalName）+ 归一化 + 稳定化的工程精度，
  才是 Gate 2 可行性与 V10 性能的真正命门**，闭包大小本身不是。

## 结论 3：归一化比对全量证明（已实现）—— V9 第 1 层 PASS

给 diff linker 加了归一化（`tools/diff_linker.py` 的 `normalize()`）：pc-relative
call/jmp 目标 → 归一成目标符号（消代码段平移）；对象池 slot `0xNN(%r15)` → 通配
`POOL(%r15)`（消 slot 漂移）；函数间 `int3` padding 过滤（消 stub 尾部填充噪音）；
对象字段偏移（`0xf(%rdi)` 等）刻意**保留**（正是要抓的真变化）。

归一化前后（同一个 V9 补丁，optimistic 模式）：

| 比对方式 | byte-changed | 闭包 |
|---|---|---|
| 原始字节 | 1184 (41%) | 1795 (62.6%) |
| **归一化** | **3** | **4 (0.1%)** |

byte-changed 塌缩到**恰好 3 个**——`sumXY` / `bumpY` / `makePoint`，正是真正读写 /
构造 Point 的函数；闭包 4 = 这 3 个 + `main`（传播）。**全量、精确地证明了"1184 里
1181 个是漂移噪音、真实闭包个位数"。**

→ **V9 第 1 层（静态完备性）PASS**：字段布局变更的访问者被**完备**（P1 已证访问者
字节必变、逐字节比对捕获不漏）且**精确**（归一化消噪后无误伤，2862 个无关函数全判
等价）识别。归一化 = 把"对齐/稳定化精度"这个命门在 spike 层面兑现的手段。

## 待办：第 2 层运行时实跑（V9 的另一半，已与用户确认）

在 Gate 1 运行时机制上真构造字段布局变更补丁，跨函数共享 Point 对象，确认无内存错乱 /
读到正确新布局；可选：故意漏转一个访问者，演示错乱以确立风险下界。需先探"补丁能否
定义 / 使用新布局类"——可能触及 [[gate1-dynamic-modules-cannot-replace]] 的限制、
需扩展 VM 补丁。

## 工具修正

`compare_fn.py` 的反汇编窗口从 0x60 加大到 0x400：0x60 对长函数只看了前半，会漏报
后半差异（本次差点据此误判 `DateTime.toString` 未变）。短函数不受影响（首个 ret 早截断）。
