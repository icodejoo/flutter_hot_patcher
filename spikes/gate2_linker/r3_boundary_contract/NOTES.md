# R3 spike级审计 —— 间接调用边界契约：diff_linker 模型本身是对的，真正的缺口在下游

**背景**：`PRODUCTION_LINKER_SPEC.md` R3 原表述是"间接/虚调/闭包/tear-off/池介导调用的显式边界
契约"，对应 REVIEW 的 S2/S4/S5/B1/B2。这轮不是重新造一个 build 实验，而是把 `diff_linker.py`
自己的设计声明、Gate1 V2 的重定向机制实测、COVERAGE_GAPS 里已有的一条残留备注，三处证据串起来，
把"这个缺口到底缺在哪一层"讲清楚——发现真正缺的不是 diff_linker 的静态分析，而是**运行时补丁
应用机制（尚未建设）的完备性**，这是一个此前被"R3"这个名字模糊掉的、更重要的区分。

## diff_linker 自己的设计声明（docstring，非本轮新发现，但需要被认真对待）

```
Failure propagates up the call graph from the byte-changed set, stopping at
virtual-call boundaries (dispatch table, redirectable — Gate 1 V2).
```

也就是说：条件2的"必须重新解释"传播**只沿直调边走，遇到虚调用/闭包调用故意不传播**。这不是
遗漏，是**设计决策**——依据是 Gate1 V2 的结论。

## Gate1 V2 的实测结论（`gate1_mixed_execution/cases/v2_call_forms_matrix/NOTES.md`）

三种调用形态的重定向点位置不同：

| 形态 | 重定向点 | 粒度 |
|---|---|---|
| 静态直调 | 每个调用点机器码 | 逐点改写 |
| 虚调用/接口调用 | dispatch table 里该 class id 的一项 | 改一处，该类所有调用点统一生效 |
| 闭包调用 | **该闭包对象实例自己的 entry_point 字段** | 改一处，**只对这一个闭包实例生效** |

前两种是"单点控制"（改一处、全局/全类生效），diff_linker 不需要为它们建传播边是**站得住的**——
只要重定向机制在 apply 阶段把 dispatch table 那一项 / 调用点改对，所有经这条路径到达changed
函数的调用方都自动获得正确行为，AOT 调用方本身完全不需要被标记"必须重新解释"。

## 真正的缺口：闭包重定向是"每个实例"粒度，不是"每个函数"粒度

第三种（闭包）不是单点控制——它是**每个闭包实例**一个重定向点。V2 的测试代码
（`v2_call_forms_matrix/host/*.dart`）只验证了重定向**一个已知的闭包变量**
（`closureVar`）：

```dart
internal.redirectClosureEntryPoint(closureVar, closureTargetPatched);
```

这证明了**机制本身有效**（改一个 Closure 实例的 entry_point 字段确实能重定向调用），但**没有
测试"如何找到所有需要被重定向的闭包实例"**——真实场景里，一个被改动的函数可能已经被 tear-off
成闭包很多次、存进多个字段/缓存/List 里，补丁应用时必须**枚举堆上所有指向该函数的活跃闭包实例**
（heap walk），才能保证"改一个点，全部生效"这个说法成立。如果某个实例存在补丁应用时"够不着"
的地方（例如：某个闭包被存进一个补丁引擎不知道要遍历的数据结构、或存在弱引用/isolate 间共享
结构里），它会**永久保留旧 entry_point、永久调用旧代码**——不是崩溃，是**悄悄地不生效**，比
崩溃更危险，因为不会有任何错误信号。

这条残留其实 `COVERAGE_GAPS.md` #2 已经点到过，但当时归类成"运行时缓存失效项，非
diff-linker完备性问题"、一笔带过：

> **运行时注意**：补丁前已缓存旧 entry 的 tear-off 闭包需 V2 式 entry 重定向刷新
> （运行时缓存失效项，非 diff-linker 完备性问题）。

这轮的贡献是把它从"一句带过的注意事项"提升成**R3 边界契约里明确的、独立的生产需求**——因为
它恰好是"哪些间接调用形态天然安全、哪些形态需要额外机制"这张边界表里唯一一个**没有单点控制**
的形态，理应被单独列出、单独设计验证方案，而不是跟 dispatch table 那种"改一处就好"的情形混为
一谈。

## 结论（对 PRODUCTION_LINKER_SPEC R3 的修正）

R3 原表述把"diff_linker 的静态调用边模型"和"运行时补丁应用的重定向完备性"混在一起。厘清后：

1. **diff_linker 的静态模型没有缺口**——虚调用/闭包调用故意不传播条件2是对的，有 Gate1 V2 实测
   支撑，不是遗漏。
2. **真正的缺口在运行时补丁应用机制**（尚未建设，属 R1-R9 之外、部署系统层面的问题）：
   - dispatch table / 静态直调：单点控制，reasoning 完整，无额外未知项。
   - **闭包 tear-off**：每实例控制，需要**堆遍历枚举所有活跃闭包实例**并逐一重定向；这一步
     "枚举完备性"从未被验证过（V2 只测了一个已知变量），失败模式是**静默不生效**（无错误信号，
     比崩溃更危险）——按用户"宁可不用也不能出问题"的原则，这应该被列为**生产化前必须专门验证
     的独立风险项**，而不是内嵌在 R3 表格里的一句注脚。

建议：`PRODUCTION_LINKER_SPEC.md` 新增一条独立需求（暂记 R3.1，"闭包重定向完备性"），要求生产
补丁应用引擎证明"给定一个被改动的函数，能枚举所有引用它的活跃闭包实例"——如果做不到完备枚举，
则该函数只要曾被 tear-off 过就必须保守地整体禁止走"改 entry_point"这条轻量重定向路径,退化到
更重的机制（例如全局替换该 Function 对象本身而非逐实例，需要验证是否可行）。
