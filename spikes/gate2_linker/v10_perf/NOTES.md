# V10 影响范围与性能 —— 关键决策数据

**问题**（PLAN §Gate2 V10）：典型改动下"受影响传递闭包"的规模、由此导致的解释比例
与性能下降幅度是否产品可接受。这是 Gate 2 与 V9 并列的两个 go/no-go 判据之一。

跑：`DART_SDK_SRC=/root/dart/sdk ./build_and_run.sh`（须在含 `test-lib` 子串的路径下，
`dart:_internal` 导入白名单，见 gate1-vm-spike skill §4）。x86-64，i5-13500，ReleaseX64。

## 拆解：V10 = 闭包规模 × k × 热度

性能下降不是单一数，是三个量的合成。端到端墙钟放慢的模型：

```
slowdown ≈ 1 + f × (k − 1)
```

- **k** = 同一份 Dart 逻辑，解释字节码 vs AOT 原生的每单位放慢倍数（← 本 spike 首次实测）。
- **f** = 应用总运行时间里落在"被转解释的闭包"里的时间占比（← 由闭包规模 + 这些函数
  有多热决定；不是静态函数个数比例）。
- **闭包规模**：P2/tools/V9 已证真实闭包个位数、有界（归一化后 0.1% 函数数）。

## 实测 1：k（解释 vs AOT 放慢倍数）—— Gate 1 从未产出的数

复用 Gate 1 的 `loadDynamicModuleClosure` + `invokeDynamicModuleClosure`，同一份核函数
一份 AOT 直调、一份编字节码走解释器，各跑 N 次比墙钟（`gen.py` 保证两侧循环体逐字节
相同；AOT 收运行时种子防常量折叠，字节码烤字面量、dart2bytecode 不折叠）。**不改调用点**
——重定向透明性 V1-V5 已证，这里只隔离解释器本身的开销。

**关键：k 不是单一常数，是"原生工作 vs 解释器 dispatch 占比"的函数。** 测三种形态
（各两次跑，确定性）：

| 形态 | 每迭代原生 | 每迭代解释 | **有效 k_work** | 说明 |
|---|---|---|---|---|
| `arith` 纯整数算术 | 2.0 ns | 28 ns | **13.6–14.1x** | 每条字节码一次 dispatch，无原生可摊——**解释器天花板** |
| `strbuild` 插值+int.parse | 4.3 ns | 50 ns | **11.6–11.7x** | 原生工作太小（+2.3ns/iter），摊不动插值展开的多条字节码 dispatch |
| `nativeheavy` 每迭代一次重原生调用（`'ab'*~130`） | 78 ns | 135 ns | **1.7–1.8x** | 单次重原生调用（~130 字符分配）主导，解释器 dispatch 被摊薄 |

每次调用固定开销（W=0）：native ~2.7ns，interp ~60ns，**比值 ~22–29x**。

**读数**：
- **k 从 ~14x（纯算术）一路降到 ~1.7x（重原生主导）**。决定 k 的是"这段代码有多少工作
  真的落在解释器逐条 dispatch 上、多少委托给原生运行时（分配/库函数/宿主 AOT）"。
- **~14x 是最坏形态（纯算术热循环）的天花板，不是典型值**。真实补丁大量做分配、字符串、
  集合、调库——这些的重活在解释路径里**仍走原生运行时**，有效 k 显著更低。
- 但"轻原生点缀"（strbuild）降得有限（11.6x）：k 显著下降只在**单次调用做足够重的原生
  工作**、把一次 dispatch 摊掉时才发生。逐条插值/小调用摊不动。
- **每次调用固定开销 ~22–29x（60ns vs 2ns）单独是个坑**：对"体量极小、被高频调用"的
  函数（getter、一行判断），主导成本是这 ~60ns 固定开销而非计算量。细粒度热点函数转
  解释比粗粒度更亏。
- 实现说明：让补丁调 dart:core（插值/int.parse/String.*）要走**官方 dynamic modules
  流程** + `dynamic_interface.yaml` 声明 `callable: dart:core`（`--dynamic-interface` /
  `--import-dill` / `--validate`）。否则闭世界树摇让这些调用在字节码**加载阶段**报
  `Unable to find function ... in dart:core`（见 gate1-vm-spike skill §6）。这也顺带
  在 spike 层面兑现了"补丁靠 dynamic_interface 调宿主/库 API"这条官方机制。

## 实测 2：真实闭包规模（沿用 P2/tools/V9）

局部改一个函数 → 传递闭包在**理想 CanonicalName 对齐**下塌缩到个位数（patchleaf=3、
V9 字段布局=3+main）；裸符号名撞名会滚到 30.9%（那是对齐精度问题，非闭包天然爆炸）。
即 **f 的分子（被转解释的函数集合）小且有界**。

## 合成：端到端下降取决于"补丁改的是不是热点"× k(形态)

两个自由度共同决定端到端墙钟 `slowdown ≈ 1 + f×(k−1)`：
- **f**（补丁函数的时间占比，≠ 函数个数占比）：3 个函数若恰是渲染/计算热循环，f 大；
  冷/温业务逻辑则 f 极小。
- **k**（该补丁形态的有效放慢，实测 1.7–14x）：纯算术热循环取上界 ~14；分配/库/委托
  原生的真实业务代码取 ~2–12。

按最坏 k≈14 代入（下界情形 k≈2 时下降只有约 1/13）：

| 补丁打在哪 | f（时间占比） | 端到端 slowdown ≈ 1+f×(k−1)，k=14 |
|---|---|---|
| 冷路径 bug（大多数线上修复：某分支逻辑、边界处理） | <1% | **<1.13x**，实际感知≈0 |
| 温路径（每帧调几次的业务函数） | ~5% | ~1.65x（局部，非全局帧率；真实业务 k 更低则更小） |
| 热内循环（每帧上万次的**纯计算**） | 逼近该循环占比 | 可达数倍——**这是要规避的形态**（纯算术正好吃满 k=14） |

## 对 Gate 2 go/no-go 的结论

- **V10 未推翻方案**，且精确划出了性能的适用边界：
  1. 解释惩罚 k 实测 **1.7x（重原生主导）～14x（纯算术，天花板）**、每调用固定开销 ~22–29x。
     **不是"慢到不可用"，而是"看补丁形态 + 打在冷路径还是热内循环"**。
  2. 真实闭包个位数、有界（V9/P2）——f 的分子天然小。
  3. 端到端墙钟 = `1 + f×(k−1)`，**两个决定量（补丁热度 f、补丁形态 k）产品都可控**：
     线上热修复绝大多数是冷/温路径逻辑 bug（f 小）且做分配/调库（k 低），下降可忽略；
     唯一危险是"改到热内循环里的纯计算"（f 大且 k 撞满 14），可识别、可规避（该类改动
     走完整重编译/重发，而非解释补丁）。
- 命门仍与 V9 一致：**对齐/稳定化精度**决定闭包大小、进而决定 f 的分子。裸名 30.9% vs
  理想 0.1% 差 300 倍——CanonicalName 对齐（SPEC §4.1）不是优化是可行性前提。

## 诚实的已知边界（留作正式研发的量化项）

1. **已测三种形态（arith/strbuild/nativeheavy）刻画了 k 的谱系（1.7–14x）**，但都是合成
   微基准，不是真实业务函数。真实补丁的有效 k 落在这个区间的哪里，取决于其"解释器
   dispatch vs 委托原生"的具体配比，须用真实补丁实测。补丁跨边界调**宿主自定义 AOT
   函数**（非 dart:core）还需在 `dynamic_interface.yaml` 里声明该宿主库/成员 callable
   并走 `--filesystem-scheme`（见 v9_field_layout/runtime），本 spike 只验证了 dart:core。
2. **f 无通用值**：是每个 app×每个补丁的具体数，须在正式研发用真实 app + 真实补丁 +
   采样 profile 实测，不能从静态函数比例推断。本 NOTES 给的是模型与量级，不是某个 app 的
   承诺数字。
3. **x86-64 桌面，非 arm64 真机**。解释器/AOT 相对开销 arm64 可能不同，量级预计一致；
   真机数字待阶段 B。
4. 每档 N 固定、外层循环 AOT，测的是稳态；未剔除 Stopwatch/边界的纳秒级噪音（k 的一位
   有效数字可信，两位不必较真）。
