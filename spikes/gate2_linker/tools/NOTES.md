# 最小 diff linker：实现与首个量化结论

`diff_linker.py` 实现 P2 确立的**两条件不动点**（见 `../probe_reloc_equivalence/NOTES.md`）：
一个函数判"等价、指回基线机器码"当且仅当 ①自身机器码逐字节等价 **且** ②它直调/
内联的所有目标也都等价。从"字节变化"集合出发，沿调用图反向传播不动点，输出"必须
转解释"的传递闭包。

跑：`DART_SDK_SRC=/root/dart/sdk ./run_diff_demo.sh`（patchleaf 场景）

## 核心逻辑验证：两条件不动点成立

patchleaf 场景（`pureLeaf` 改一个常量 `x*3+1→x*3+2`，其余源码不变）：
- `pureLeaf`：字节变化 → 条件 1 命中，进闭包。
- `caller`：字节**完全相同**，但直调 `pureLeaf`（∈闭包）→ 条件 2 传播，进闭包。**✓**
- `callsLib`：字节相同，只调未变的库函数 → 判等价。**✓**

条件 2 的传播正是 P2 那个"字节等价但必须转解释"陷阱的正确解法。

## 首个量化结论：闭包不爆炸，对齐精度才是命门

同一个改动，两种符号对齐精度下的传递闭包规模：

| 对齐方式 | 转解释函数 | 占比 |
|---|---|---|
| 保守（裸符号名，撞名兜底转解释） | 886 | **30.9%** |
| 理想（假设 CanonicalName 精确对齐） | 3 | **0.1%** |

**差 300 倍，全部来自符号对齐是否精确。**

- 裸 AOT 符号名**不唯一**：本例 2864 个函数里 **345 个（12%）撞名**——4 个不同库的
  `main`，以及大量跨库/跨类同名的 `toString`/`==`/私有方法。裸名无法把新旧版本的
  同一函数可靠对齐，保守策略只能把所有撞名函数判为"可能变了→转解释"，再沿调用图
  把它们的调用者全拖进闭包，滚成 30.9%。
- 一旦假设理想对齐（撞名能被 CanonicalName 区分、判未变），真实闭包塌缩到 **3 个
  函数**（`pureLeaf` + 直调它的 `caller` + 1 个调 `caller` 的），**0.1%**。

## 这对 Gate 2 可行性的意义

Gate 2 的核心疑虑之一（SPEC 风险清单）是"多层内联下传递闭包可能很大、解释比例失控"。
本实验给出的方向性答案：**闭包本身有界且极小**（一个局部改动 → 个位数函数）；**解释
比例失控的真正来源是对齐 / 稳定化不精确**，不是闭包天然爆炸。因此：

- SPEC §4.1 的 **CanonicalName 对齐**、§4.3 的 **cid 稳定化**不是"锦上添花的优化"，
  而是**决定解释比例、进而决定方案是否可行的命门**。V10 的性能数字本质上是"对齐/
  稳定化精度"的函数。
- 下一步要测准真实闭包规模（V10）、以及做 V9 的字段布局闭包，都**必须先把符号对齐
  从裸名升级到 CanonicalName**（从 Kernel `.dill` 层拿 库URI→类→成员 的唯一路径，
  与 AOT 符号建立映射）。这是 Gate 2 目前识别出的最硬工程点。

## 已加入：归一化比对（V9 引入，见 `../v9_field_layout/NOTES.md` 结论 3）

`normalize()` 在逐字节比对前剥掉漂移噪音：pc-relative call/jmp 目标→目标符号（消
代码段平移）、对象池 slot `0xNN(%r15)`→`POOL(%r15)`（消 slot 漂移）、`int3` padding
过滤（消 stub 尾部填充）；对象字段偏移刻意保留。V9 场景下把假 byte-changed 从
**1184 塌缩到 3**（真访问者），闭包 62.6%→0.1%。这是把"对齐/稳定化精度"命门在
spike 层面兑现的手段。

## spike 工具局限（须知）

- **归一化的 pool-slot 通配是近似**：把 `0xNN(%r15)` 无条件通配成 `POOL`，会**漏报**
  "两版引用了池里不同常量"这类真实差异（例如补丁改了一个字符串字面量、但访问它的
  指令结构没变）。真实 linker 必须做**精确的 slot→常量映射**（解析对象池内容，比较
  两版同一 slot 的常量是否相同），而不是通配。spike 里通配是为了先量化"漂移噪音占比"，
  不是最终方案。补这个精确映射时要小心不要把它做成新的漏报源。
- **裸符号名对齐**（撞名 12%）——这正是被本实验暴露、需要升级为 CanonicalName 的点。
- x86-64、基于 `objdump`；只跟踪能解析到具名符号的 direct call，间接调用
  （`call *off(%r14)`，VM runtime stub，非补丁可替换目标）忽略。
- 未处理内联（条件 2 的"内联"分支）：内联使被内联函数的代码直接嵌进调用者，调用者
  字节因此变化，会被条件 1 直接捕获，但 spike 未单独验证多层内联的闭包形状（留待 V7）。
