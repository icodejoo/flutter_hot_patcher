# Gate 2 — Linker（逐函数差分替换）spike

验证难点 Y（PLAN.md / SPEC.md §4）：基线全优化 AOT 编译下，linker 能否正确识别
"受影响传递闭包"并转解释执行，使补丁行为与完整重编译版一致，且解释比例导致的
性能下降可接受。

**这不是要做出完整 linker**（那是正式研发阶段的 1–2 人月工程）。和 Gate 1 spike
一样，目标是用最小实验对每个验证用例回答"这个机制在这种情况下会不会成立"，尤其
V9（类字段布局变更，最可能推翻方案的用例）。

## 验证用例（PLAN.md）

| 用例 | 内容 | 状态 |
|---|---|---|
| P1 | 探路：AOT 如何编码实例字段访问偏移 | ✅ 见 `probe_field_layout/` |

另：机器码替换路线调研见 `research_machinecode_route.md`（用户择日再深议）。

## 通过 / 放弃判据（PLAN.md）

- ✅ 通过：V6–V9 正确 **且** V10 性能下降产品可接受 → 进入正式研发。
- ❌ 放弃：V9（字段布局）无法可靠解决，或解释比例失控致性能不可接受，或替换频繁
  出现难以预测的错误 → 放弃 iOS 自研。

## 与 Gate 1 的关系

Gate 1 已验证"混合执行 ABI"：AOT 调用点可运行时重定向到解释执行的字节码，且静态
直调 / 虚调用 / 闭包三种形态都能重定向（V2）。Gate 2 复用这个结论——"哪些入口可
重定向、哪些必须连带失效"是 Gate 2 传递闭包分析的基础。Gate 1 的 VM 补丁
（`../gate1_mixed_execution/vm_patch/`）和自编译 Engine 是 Gate 2 的运行时底座。

## 环境

沿用 Gate 1 的 WSL2 + dart-lang/sdk 桌面构建（`out/ReleaseX64`）。探路阶段在桌面
x86-64 上做（反汇编、布局分析与架构无关）；真正的行为验证需要时再上 arm64 / 真机。
