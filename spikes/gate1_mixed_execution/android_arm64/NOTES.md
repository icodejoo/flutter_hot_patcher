# Gate 1b — Android arm64 真机复现总览

V1-V5 在 x86-64 桌面全部验证通过后（见 `../cases/`），本目录在真实 Android arm64
设备上逐个复现，作为 iOS 真机复验（阶段 B）前的低成本预检查。**明确边界**：
Android 不强制 W^X，这里通不通答不了 iOS 最核心的悬念（`mprotect(PROT_EXEC)`
会不会被系统拦截）；这里只回答"核心机制的思路能不能跨架构复现、arm64 特有的
指令编码/内存一致性细节要怎么处理"。完整背景见 `../GATE1_REPORT.md` 第 12 节。

设备：华为 STG-AL00，arm64-v8a，Android 12（SDK 31）。

## 结果汇总

| 用例 | 桌面 x64 结果 | Android arm64 结果 | 需要 arm64 专属改动？ |
|---|---|---|---|
| V1 替换既有函数 | PASS | **PASS** | 需要（调用点改写 + icache 刷新，见 `v1_replace_existing_function/NOTES.md`） |
| V2 三种调用形态矩阵 | PASS | **PASS** | **不需要**——`host/main.dart` 原样拷贝跑通 |
| V3 异常穿透 | PASS | **PASS** | 需要（复用 V1 的改写机制，泛化到两个调用点） |
| V4 补丁内触发 GC | PASS | **PASS** | 需要（复用 V1 的改写机制） |
| V5 压测（高频+并发） | PASS | **PASS** | 需要（复用 V1 的改写机制 + isolate 并发，机制本身架构无关） |

## 关键结论：V2 的可移植性验证了 V2 桌面阶段的矩阵预判

V2 桌面版的 `NOTES.md` 早就总结过一张矩阵：静态直调的重定向点是"调用点机器码"
（架构相关，V1/V3/V4/V5 都要单独处理），而虚调用/接口调用的重定向点是"dispatch
table 一项"、闭包调用的重定向点是"Closure 对象的 entry_point 字段"——这两个都是
**通过 VM 原生函数操作 Dart 对象**，不碰任何原始机器码或指令编码。这次在 Android
arm64 上原封不动跑通 V2（零改动），**实测验证了这条矩阵的可移植性推论**：
只要重定向点是"改一个 VM 管理的数据结构字段"而不是"改机器码"，这套机制天然
跨架构，不需要为每个目标平台单独适配。这是这次 Gate 1b 复现里除"V1 机制可行"
之外最有分量的一条附加证据。

## arm64 特有的实现细节（V1/V3/V4/V5 共用，完整解释见 v1 的 NOTES.md）

- 直调指令是 `bl`（不是 x86 的 `call rel32`），反汇编实测确认编码。
- arm64 自修改代码需要显式刷新指令缓存；bionic 没有现成的
  `__clear_cache`/`cacheflush` API，自己写汇编、用 NDK 交叉汇编器验证字节、
  `mmap` 出可执行页调用。
- 设备无 `nm`，地址解析挪到构建期在宿主机完成，通过命令行参数传入。

## 踩坑：`@pragma('vm:entry-point')` 函数在符号表里出现两次

`fAlt()` 标了 `@pragma('vm:entry-point')`（保活用，防止 AOT 树摇删掉它），
结果在 arm64 的 `nm` 输出里出现了**两个不同地址**的 `fAlt` 符号（大概率是
checked/unchecked 两个入口变体）。构建脚本用 `awk '$3=="fAlt"{print $1}'`
匹配出两行，赋值给 shell 变量时中间嵌入了一个换行符，传给 `adb shell` 的
命令字符串被这个换行拆成两条命令——第二条("一串十六进制地址")被
`/system/bin/sh` 当成命令名执行，报 `inaccessible or not found`。

**这不是随机噪音，是必现的**：第一次跑 V1 时这个错误就出现过，当时因为
"侥幸"选中的是两个地址里 nm 排在前面的那个（较低地址），程序碰巧正确所以
被忽略了。第二次在 V3 上复现时才顺藤摸瓜查到根因（`nm` 对同一符号名给出
两行不同地址）。**修复**：所有取地址的地方都加 `| head -1`，确保只取一行、
不依赖排序侥幸。**没有验证过两个地址具体对应什么**（checked entry vs
unchecked entry 只是推测，没有反汇编逐一确认）——按现在的证据，用较低地址
（`nm` 默认按地址升序排列时排在前面的那个）能让重定向正确工作，足够支撑
这次验证目的，但如果以后要在生产级 linker 里做类似的符号解析，需要先查清楚
这两个地址分别是什么、该用哪一个，不能继续沿用"选第一个"这个经验规则。
