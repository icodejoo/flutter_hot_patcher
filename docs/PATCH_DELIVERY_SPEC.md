# PATCH_DELIVERY_SPEC — 补丁下发全链路规格

补丁生成 → 签名 → 下发 → 客户端应用 → 回滚 的服务端/全链路架构
版本 v0.1 · 2026-07-31

> ⚠️ **本文是设计草案，不是已拍板的最终方案。** 凡是存在多个同样合理实现路径的地方，都在
> 正文标注为「决策点」并在 §8 汇总，等待用户拍板；只有在**安全上没有退让空间**的地方（签名
> 验证失败必须拒绝、版本不匹配必须拒绝等）才直接下结论。落地实现排在 iOS Gate 通过之后
> （见 §9 与 `PLAN.md`），当前只做设计，不动工程。

## 0. 定位与边界

### 0.1 本文解决什么

`PRD.md` §2 承诺「全链路私有部署——补丁生成、签名、下发、回滚均在自有基础设施内完成」，
`SPEC.md` §6 给了签名/provenance/传输的**要点**，但**补丁包长什么样、密钥怎么轮换、客户端
怎么灰度、怎么熔断回滚**这一整块从未展开设计。本文补齐这块，且**与 iOS/Android 底层 VM 机制
完全解耦**——不依赖 Gate1 阶段 B（iOS W^X）的验证结果，现在就能设计。

### 0.2 复用的既有结论（不重复论证，只引用）

| 既有结论 | 出处 | 本文如何依赖 |
|---|---|---|
| 补丁需**冷重启**才生效，且生效状态持续到下次正式发版 | PRD §7、SPEC §5.5 | 决定了「应用」和「回滚」都只能在下次冷启动落地，不能即时热切换（§4、§5） |
| Linker 产出的不是「变化函数列表」，而是**新程序完整入口表** + 需携带的字节码 | SPEC §4、§5 | 决定了补丁包里装什么（§1） |
| 补丁字节码引用的符号受**闭世界树摇**限制，只能绑定基线已保留的符号 | GATE1_REPORT §6.3 | 决定了「补丁必须对准某个**具体** build，装错版本符号绑定假设就不成立」（§3.3） |
| 增删类会导致 **cid 全局漂移**，装错基线会读到错位内存 | SPEC §4.3、§9 | 决定了版本匹配校验是**安全红线**而非优化项（§3.3） |
| 补丁应用需完备枚举堆上所有引用被改函数的闭包实例（`HeapIterationScope`） | R3.1、r3_closure_enum_probe | 决定了「应用」必须**全有或全无**：枚举不完备 = 应用失败，禁止部分应用（§4.4） |
| 补丁用私钥签名、端上内置公钥校验、provenance 绑定 SDK 版本+校验和 | SPEC §6 | 本文把这三行要点展开成完整签名/信任/轮换/泄露应急方案（§2、§3.3） |

### 0.3 非目标（对齐 PRD §3，本文不越界）

- **不假设服务端有用户系统 / 账号体系**。PRD §3 排除「通用动态化框架」，本方案只服务「自有 App
  的新旧版本差分」这一封闭场景。灰度分桶因此**默认走客户端侧**，不引入设备注册表/用户身份（§3.2）。
- **不覆盖 assets / native 热更**（PRD §3）——补丁包格式里没有资源/`.so` 通道（Android 长期
  的原生差分 `.so` 是 SPEC §7.1 暂缓项，本文只在格式里预留 `payload_type` 字段，不展开）。
- **不绑定任何云厂商 / KMS 产品**。全文只到「私钥离线保管、公钥内嵌」这个架构层面，不写死用
  哪家密钥托管服务——这是「可私有化部署」承诺的底线。

### 0.4 威胁模型（贯穿全文的设计假设）

热修复本质是**绕开应用商店审核、直接给用户设备推送可执行内容**。签名/校验环节一旦有漏洞，
攻击者能借这条通道给全量用户推任意恶意代码——是能上新闻的安全事故。因此设计时**必须假设**：

- **CDN / 下发服务器可能被攻破**：不能因为「文件是从我们服务器下来的」就信任它。
- **传输链路可能被中间人**：TLS 是必要不充分条件，不能作为唯一完整性保证。
- **构建产物可能在服务端被篡改**：补丁在离开构建机之后的每一跳都可能被换掉。

**核心原则：端上信任的根，只有编译进二进制、离线保管私钥对应的那把内嵌公钥。**
「下发通道安全了就默认补丁可信」是本文明确拒绝的单点信任模型——每一层都要有**独立**的
完整性保证（§6 汇总）。

## 1. 补丁包格式

### 1.1 结构：清单 + 内容寻址产物

补丁包不是一个不透明的二进制大块，而是**一份清单（manifest）+ 若干被清单以哈希引用的产物**。
签名只签清单；清单里逐条列出每个产物的密码学哈希。这样任何一个产物在 CDN 上被单独替换，
都会导致哈希对不上而被拒——这是「不单点信任下发通道」的第一层落地。

```
patch_bundle/
├── manifest.json          # 清单：元数据 + provenance + 所有产物的哈希；被签名的唯一对象
├── manifest.sig           # 对 manifest.json 规范化字节的分离式签名
├── bytecode/              # dart2bytecode 产出的差分闭包字节码
│   └── *.bytecode
├── entry_table.bin        # Linker 产出的新程序完整入口表（函数→基线机器码 / 解释器 stub）
├── canonical_map.bin      # CanonicalName 映射表（符号绑定用，见 §1.3）
└── cid_map.bin            # cid 稳定映射（SPEC §4.3，避免装载后 cid 漂移）
```

### 1.2 manifest.json 字段（决定「装什么、对准谁」）

```jsonc
{
  "patch_id": "…",              // 全局唯一，回滚黑名单/熔断以此为键
  "patch_version": 7,           // 同一 base 下单调递增，用于「新补丁取代旧补丁」判定
  "created_at": "…",            // 构建时间戳（审计用，非信任凭据）
  "platform": "ios | android",  // 见 §1.4 平台差异
  "payload_type": "bytecode",   // 预留：future Android 可为 "native_so"（SPEC §7.1，暂缓）

  // ── provenance / 版本绑定（SPEC §6，安全红线，见 §3.3） ──
  "target_build_fingerprint": "…", // 本补丁**只能**装在这个 build 上；不匹配必须拒绝
  "sdk_version": "…",              // dart-sdk / engine 锁定版本（MAC_HANDOFF §1）
  "baseline_snapshot_digest": "…", // 基线机器码池的校验和

  // ── 产物完整性（每个产物一条哈希，签名经清单间接覆盖全部产物） ──
  "artifacts": [
    { "path": "bytecode/…", "sha256": "…", "size": … },
    { "path": "entry_table.bin", "sha256": "…", "size": … }
    // …canonical_map / cid_map 同理
  ],

  // ── 签名元信息（见 §2） ──
  "sig_anchor_key_id": "…",     // 用内嵌锚点集里的哪把锚点作验签起点；多锚点并存做轮换（§2.4）
  "sig_alg": "…",              // 签名算法族（决策点 D5）
  "cert_chain": [              // 可选、长度可变：直签模式（链长 0）为空/省略；根+子密钥模式（链长 1）带一张根签发的子密钥证书（§2.3）
    { "key_id": "…", "subject_pubkey": "…", "not_before": "…", "not_after": "…", "sig_by_parent": "…" }
  ]
}
```

**关键设计**：`target_build_fingerprint`、`baseline_snapshot_digest` 等 provenance 字段是
**清单的一部分**，因此被签名覆盖。攻击者即使拿到一个合法签名的补丁，也**无法把它重新指向
另一个 base 版本**——改 fingerprint 会破坏签名。这一条把「版本绑定」从「客户端自觉检查」
升级成「密码学强制」。

### 1.3 为什么要带 canonical_map（符号绑定的落地）

GATE1_REPORT §6.3 已证明：补丁字节码引用的每个符号，必须在基线 AOT 产物里**已被保留**，
否则字节码**加载阶段**就报 `Unable to find …`。因此补丁包必须携带 CanonicalName 映射表
（来源见 `r1_kernel_dill_probe`：`package:kernel` 读出的 `package:xxx/yyy.dart` 稳定 URI），
让客户端加载器把补丁常量池里的符号引用，绑定到基线快照内**同一 CanonicalName** 的实体。

**构建期义务（linker，非客户端）**：linker 生成补丁时**必须**核验补丁引用的每个符号在
`target_build_fingerprint` 对应的基线里确实保留；核验不过 → **拒绝生成补丁**（对齐
「宁可不生成补丁也不能出问题」的安全原则）。客户端只做「fingerprint 匹配」这一道校验，
不重新做符号可达性分析——匹配成功即意味着「这份补丁是针对我这个 build 的符号集算出来的」。

### 1.4 iOS / Android 是否需要不同格式

- **当前主线（iOS + Android 差分解释）：格式相同**。两端都是「字节码 + 入口表」，走解释器
  路线，`payload_type = "bytecode"`。差异只在 §7 平台约束（iOS 只能解释、Android 也可解释），
  不在补丁包结构。
- **Android 长期方向（SPEC §7.1，暂缓）**：若未来 Android 走「差分 + 原生重定向」，产物会
  多一个 `native_so`，`payload_type` 字段就是为此预留的**扩展位**，本文不展开其格式（依赖
  尚未开建的生产 linker R1-R9）。

## 2. 签名方案

### 2.1 信任模型：内嵌公钥 + 离线私钥

对齐 Sparkle / TUF 等成熟自更新方案的信任模型，并结合本项目「可私有化部署、无云依赖」约束：

- **私钥只在构建服务器 / CI 持有**，离线保管，绝不进代码库、绝不下发（对齐 CLAUDE.md 安全
  标准：不硬编码密钥）。
- **公钥随 App 一起编译进二进制**——它是端上**唯一**的信任根。公钥内嵌意味着「换公钥 = 发版」，
  这是本模型的根本约束，直接影响 §2.4 轮换和 §2.5 泄露应急。
- **签名对象是 `manifest.json` 的规范化字节**（固定序列化：键排序、无多余空白），清单又经哈希
  覆盖全部产物 —— 一次签名验证即认证了「元数据 + provenance + 所有字节码/入口表」的完整性。

### 2.2 验证失败的客户端行为（安全红线，不留退让）

**签名验证失败 → 必须拒绝应用该补丁，以纯基线状态启动。绝不允许「验证失败但还是试着跑跑看」。**

同样 fail-closed 的还有（任一不通过即拒绝、退回纯基线，不部分应用）：

1. 清单签名验证失败 / 公钥 key_id 不认识。
2. 任一产物哈希与清单不符。
3. `target_build_fingerprint` 与本机运行 build 不匹配（§3.3）。
4. 补丁 id 在本地黑名单里（§5.2）。

这条是整个方案的地基：**任何完整性/真实性/版本校验不通过，一律 fail-closed 回退纯基线**，
不存在「降级尝试」。宁可这次不打补丁，也不能带着未经验证的可执行内容启动。

### 2.3 签名信任结构：统一的可变长证书链（D3 已决策 2026-07-31）

**决策**：不在「单层」和「两层」之间二选一，而是让两者在**同一套验证逻辑**下共存——把两层
方案里的「证书链」抽象成**可选的、长度可变**的东西，单层就是**链长为 0** 的退化情形。每个
**App 项目在各自构建期**选定自己适用的模式（简单/低价值 App 走链长 0，复杂/高价值 App 走
链长 1），客户端只有一套通用的链式校验代码，没有两条互斥分支。

#### 2.3.1 两种模式是同一模型的两个长度

| 模式 | 证书链长 | App 内嵌的锚点是 | 验证路径 |
|---|---|---|---|
| **直签**（原单层方案 A） | **0** | 日常**签名公钥**本身 | 内嵌锚点**直接**验清单签名，不涉及任何证书 |
| **根+子密钥**（原两层方案 B） | **1** | 极少使用、离线冷存的**根**公钥 | 先用根验补丁携带的子密钥证书，再用子公钥验清单 |

- 直签模式简单、依赖少、无证书有效期/吊销管理开销；但签名私钥泄露只能靠紧急发版换锚点（§2.5）。
- 根+子密钥模式多一层复杂度和证书生命周期管理；换来**轮换/吊销子密钥不需要发版**、私钥泄露
  恢复面缩小到「吊销子证书」（§2.4/§2.5）。
- 泛化预留：链长现只用 0 或 1，模型本身支持固定 N（如未来要 根→中间→叶子），但当前不展开。

#### 2.3.2 构建期烧录的信任拓扑（不是运行时开关）

一个 App 二进制在**构建期**烧录两样东西，二者共同定义这个 App 的**信任拓扑**：

- `TRUST_ANCHORS`：一组 `{key_id, pubkey}` 锚点（多锚点用于轮换，见 §2.4）。直签模式里锚点
  就是日常签名公钥；根+子密钥模式里锚点是根公钥。
- `TRUST_CHAIN_LEN`：**编译期常量**，声明这个 App **要求**的证书链长度（直签 = 0，根+子密钥
  = 1）。这是两种模式**唯一**的差别所在。

> **「按 App 情况选用」= 不同 App 项目各自构建时选模式，绝不是同一个 App 运行时切模式。**
> `TRUST_CHAIN_LEN` 和锚点角色是**编译进二进制的常量**，读二进制即可确定，不随任何网络/补丁
> 输入变化。客户端代码里**没有任何一条路径**会从补丁里读取「该用哪种信任模式」——补丁只能
> 提供证书链**本身**，改变不了这个 App 对链长的要求。

#### 2.3.3 一套通用校验逻辑（链长 0 是循环零次）

客户端对每个补丁走**同一段**校验，模式差异只落在一次**链长边界检查**上：

```python
def verify_patch(manifest, sig, cert_chain):
    # 1) 起点锚点由二进制烧录，不由补丁挑选
    anchor = TRUST_ANCHORS.get(manifest.sig_anchor_key_id)
    if anchor is None:                       # 不认识的锚点 key_id
        reject()                             # → fail-closed（§2.2）

    # 2) 链长必须严格等于编译期烧录值 —— 两种模式唯一的分叉，且补丁无法拓宽
    if len(cert_chain) != TRUST_CHAIN_LEN:   # 直签=0 / 根+子密钥=1，越界即拒
        reject()

    # 3) 通用链式校验：从锚点逐级走到叶子（TRUST_CHAIN_LEN==0 时循环体一次都不执行，signer 仍是锚点）
    signer = anchor
    for cert in cert_chain:
        if not verify(cert.sig_by_parent, by=signer):  reject()   # 证书须由上一级签发
        if now() not in [cert.not_before, cert.not_after]: reject()  # 证书有效期
        if cert.key_id in local_revoked_set:  reject()             # 子证书吊销（§2.5）
        signer = cert.subject_pubkey

    # 4) 用走到的叶子公钥验清单签名（直签模式下 signer 自始至终就是锚点本身）
    if not verify(sig, canonical_bytes(manifest), by=signer):
        reject()

    accept()
```

关键点：第 2 步用 `!=`（严格相等）而非 `<=`——**既挡下降级**（根+子密钥 App 被喂零长链，想
绕过吊销层）**也挡意外升级**（直签 App 被喂一条链，想混淆 key_id/审计语义）。直签模式下第 3 步
的循环体执行 0 次，`signer` 恒为锚点，第 4 步等价于「内嵌公钥直接验清单」——和两层共用同一段
代码，不是两个 if/else 分支。

#### 2.3.4 为什么必须堵死「运行时切模式」（这是真实安全隐患）

若允许同一 App 依补丁**呈现的内容**在 0 长 / 1 长之间自适应（即第 2 步放成「链长任意皆可」），
等于把「我的信任模型里有没有一个可吊销的子密钥层」这个决定权，交给了**攻击者可控的输入**：

- 根+子密钥模式的吊销保证，前提是**叶子子密钥永远在验证路径上**——一旦能被诱导接受零长链，
  验证起点退化成「根直接验清单」，整个吊销层被绕过。
- 直签模式若能被诱导接受一条链，锚点被当成「根」，`key_id`/审计语义随之被混淆，泄露后的
  责任界定和撤销范围都会失真。

因此链长边界必须是**不可协商的编译期常量**，越界一律 fail-closed（与 §2.2 签名失败同级）。
一个二进制的信任拓扑是确定且可从二进制本身证明的，绝不由网络输入决定。

### 2.4 密钥轮换

轮换在统一模型下沿用「多锚点并存」，两种模式换的东西不同、但都**不改变 `TRUST_CHAIN_LEN`
和锚点角色**（那是构建期固定的拓扑，轮换动不了它——不会把直签 App 轮换成根+子密钥 App）：

- **多锚点并存**：`TRUST_ANCHORS` 是一个**集合**（每把带 `key_id`），清单里的
  `sig_anchor_key_id` 指明用哪个锚点作验签起点。新旧补丁在轮换窗口内并存——老 App 认老锚点、
  新 App 两把都认。
- **直签模式（链长 0）**：轮换签名密钥 = 一次 App 发版（把新公钥加进内嵌 `TRUST_ANCHORS`），
  发版铺开后停用老私钥。轮换周期受发版节奏制约。
- **根+子密钥模式（链长 1）**：轮换子密钥**无需发版**——根签发一张新的子密钥证书（新 `key_id`
  + 新有效期），补丁改带新证书即可，内嵌根锚点不变。旧子证书到期或被吊销即退役。

### 2.5 私钥泄露应急预案

私钥泄露 = 攻击者可给全量用户推任意恶意补丁，**灾难级**。恢复能力由该 App 构建期选的模式决定：

- **通用第一步（两模式都适用）**：立即通过**签名的撤销通道**（§5.1 CRL 式 signed denylist）把
  **非预期 patch_id** 拉黑 / 把下发端切到只发「空补丁（回退纯基线）」。但撤销通道本身若也用
  泄露的那把密钥签就失效了——所以**撤销的信任根必须独立于被泄露的密钥**。这一点在两种模式下
  的落地不同：
  - **根+子密钥模式**：天然满足——撤销令用**根密钥**签，泄露的是子密钥则撤销依然可信；把子证书
    `key_id` 加进吊销集（§2.3.3 循环第 3 步），再签发新子证书即可。
  - **直签模式**：只有一把锚点密钥，它泄露后就不能再用它签撤销令（同源失效）。两条出路，构建期
    显式取舍：(i) **额外烧录一把专用撤销锚点**（与签名锚点分离、仅用于验签 denylist），让撤销在
    直签模式下也独立于签名密钥；(ii) 不额外烧录，则接受「撤销与签名同命运」，泄露只能靠紧急发版。
    也就是说：「撤销信任根是否独立」在根+子密钥模式是**免费自带**的，在直签模式是一个**要显式
    决定**的构建期选项。
- **直签模式泄露恢复**：紧急发版，从 `TRUST_ANCHORS` 移除泄露锚点、换新锚点。发版铺开前的窗口期，
  泄露密钥仍能对**未更新的老 App** 推恶意补丁——这是直签模型无法回避的暴露窗口，是选它的已知代价。
- **根+子密钥模式泄露恢复**：用离线根密钥**吊销泄露的子证书**、签发新子证书，**不需要发版**，
  暴露窗口显著更短。

> D3 已决策（§8）：两种模式在同一可变长证书链协议下共存，逐 App 于构建期选定。信任拓扑一旦
> 发版即固化（`TRUST_CHAIN_LEN` + 锚点烧进二进制），所以模式选型要在该 App 写第一行下发代码
> 之前定；但这是**每个 App 各自**的决定，不是全项目一次性的二选一。

## 3. 下发协议

### 3.1 客户端如何得知有新补丁（决策点 D1：轮询 vs 推送）

- **方案 A：轮询**。客户端在**冷启动时**（以及可选的运行期定时）向下发服务请求「当前 build
  指纹下、命中我灰度分桶的、最新补丁清单」。简单、离线友好、无需推送基础设施。
- **方案 B：推送**。服务端主动推「有新补丁」信号，客户端再拉。延迟低；但需要推送通道 + 设备
  可达性管理。

> 倾向：**补丁只在冷重启生效（PRD §7）**，因此「实时性」价值有限——即便推送秒到，也要等用户
> 下次冷启动才生效。**轮询（冷启动时拉一次）天然对齐这个约束**，推送的低延迟优势在这个场景里
> 基本用不上。倾向 A，但交用户定；若产品要「用户手动触发检查更新」，A 也能覆盖。

### 3.2 灰度发布（决策点 D2：客户端分桶 vs 服务端按设备 ID）

灰度维度支持三种圈定方式，可组合：**百分比**（放量 5%→20%→100%）、**App 版本**（只对某个
基线 build 下发）、**设备维度**（OS 版本 / 机型 / 地区等粗粒度标签）。分桶怎么做有两条路：

- **方案 A：客户端侧随机分桶**（倾向）。客户端首次启动生成并持久化一个**本地随机种子**，用
  `hash(seed, patch_id) % 100 < rollout_pct` 自行判断是否命中放量。**不需要服务端认识任何
  设备身份**——契合 PRD §3「不引入用户系统」的非目标。代价：服务端只能控制**目标百分比**，
  拿不到「精确命中了哪些设备」，也做不到「定向给某台设备下发」。
- **方案 B：服务端按设备 ID 分桶**。客户端上报一个设备标识，服务端决定给谁。能精确控制、可
  定向；但**引入设备身份 / 注册表**，逼近 PRD §3 排除的用户系统边界。

> 倾向 A（守住「无用户系统」非目标）。若产品确有「定向灰度 / 精确名单」硬需求，再权衡是否接受
> B 带来的设备身份成本——这是产品诉求 vs 架构纯粹性的取舍，交用户定。

### 3.3 补丁与 base 版本的兼容性校验（安全红线）

**这是本协议里最不能松的一环，直接关联 Gate2 的「cid/dispatch 布局漂移」风险。**

- 每个正式 build 在构建期烧入一个 **`build_fingerprint`** = 基线快照 + SDK/engine 锁定版本
  （MAC_HANDOFF §1）+ 入口表基准 的哈希。补丁清单声明它**针对哪个 fingerprint** 生成。
- 客户端下发/应用前，**逐字节比对补丁的 `target_build_fingerprint` 与本机 fingerprint**：
  - **完全一致** → 允许继续。
  - **不一致** → **拒绝，绝不硬装**。

**为什么必须拒绝而不是硬装**：补丁的入口表、cid 映射、符号绑定全部是针对**那一个具体基线**
算出来的（GATE1_REPORT §6.3 符号绑定 + SPEC §4.3 cid 稳定化）。装到布局不同的基线上，轻则
符号绑定失败报错，重则 cid/字段偏移对不上、读到错位内存——**装错版本比「没打补丁」更危险**
（没打补丁只是没修，装错版本是主动引入内存错乱）。故版本不匹配是 fail-closed 红线，与签名
失败同级（§2.2）。

- 下发服务应在**服务端也按 fingerprint 过滤**（只把匹配的补丁清单发给客户端），把不匹配挡在
  网络层，减少客户端做无用下载；但**服务端过滤是优化，不是信任来源**——客户端的 fingerprint
  校验才是最终关卡（服务端可能被攻破，§0.4）。

## 4. 客户端应用流程

### 4.1 完整链路（下载 → 校验 → 暂存 → 冷启动应用）

```
[运行期 / 冷启动] 轮询下发服务，命中灰度且 fingerprint 匹配
      │
      ▼
1. 下载补丁包到暂存区（staging，与生效目录隔离）
2. 校验清单签名（§2.2）……………………………… 失败 → 丢弃，纯基线（fail-closed）
3. 逐产物校验哈希（§1.1）……………………………… 失败 → 丢弃，纯基线
4. 校验 target_build_fingerprint 匹配（§3.3）… 失败 → 丢弃，纯基线
5. 校验 patch_id 不在本地黑名单（§5.2）……… 命中 → 丢弃，纯基线
      │  全部通过
      ▼
6. 标记为 "next-boot 补丁"（对齐 SPEC §5「Updater 检查 next-boot 补丁路径」）
      │
      ▼
[下次冷启动] Updater 发现 next-boot 补丁 → 应用（PRD §7：重启生效）
      │
      ▼
7. 按入口表建立程序视图：等价函数→基线机器码，其余→解释器 stub（SPEC §5）
   - 静态直调重定向（Gate1 V1）
   - dispatch table 项 / Closure entry_point 重定向（Gate1 V2）
   - 堆遍历完备枚举并重定向所有相关闭包实例（R3.1，HeapIterationScope）
```

**下载/校验（步骤 1-5）在运行期做；实际应用（步骤 7）只在下次冷启动做**——这是 PRD §7
「补丁需重启生效」在流程上的直接体现，不做运行期热切换。

### 4.2 暂存与生效隔离

补丁下到**暂存区**，校验全过后才「提交」为 next-boot 补丁。这样：下载中断/校验失败**绝不
污染**当前生效状态；当前会话继续以已生效的补丁（或纯基线）运行，不受下一个补丁下载过程影响。

### 4.3 应用失败必须能安全回退到「完全没打补丁」

**应用（步骤 7）任一步失败 → 必须能干净回退到纯基线启动，不能半吊子。** 因为应用发生在冷
启动早期（App 业务逻辑跑起来之前），一次失败的应用 = **这次就以纯基线启动**，next-boot 标记
清除或降级为「待确认失败」（§5.2 熔断）。绝不允许「入口表改了一半、闭包只重定向了一部分」
就继续跑——那正是最危险的静默不一致状态。

### 4.4 应用必须是「全有或全无」（原子性，红线）

这一条直接来自 R3.1 的安全底线：闭包重定向是**每实例**粒度，漏掉任何一个实例会**静默保留
旧代码、无任何错误信号**（比崩溃更危险）。因此：

- 应用引擎必须能**证明**「被改函数的所有活跃引用点（调用点 / dispatch 项 / 闭包实例）都已
  重定向」才算成功。
- **若无法完备枚举**（如 R3.1 诚实边界里的多 isolate 场景、或堆遍历中途失败）→ **判为应用
  失败，退回纯基线**，绝不「尽力而为地部分应用」。
- 这与「安全优先于功能」一致：完备性（不漏判/不漏改）永远高于「让补丁看起来生效了」。

## 5. 回滚机制

回滚有两条独立触发路径：**服务端主动下线**（§5.1）和**客户端自检崩溃熔断**（§5.2）。两者都受
「补丁只在冷重启生效」约束——**回滚同样只能在下次冷启动落地**，无法即时撤销正在运行的会话。

### 5.1 服务端「一键下线」

- 服务端把某 `patch_id` 标记为 **withdrawn**。客户端下次轮询/启动时发现「当前生效补丁已被下线」
  或「已有取代它的新补丁」→ 下次冷启动回退到基线（或加载取代补丁）。
- **撤销指令必须签名**（CRL 式 signed denylist）：撤销令用**与日常签名独立的信任根**签发
  （根+子密钥模式下用根密钥；直签模式下用 §2.5 的专用撤销锚点），下发一份「已撤销 patch_id
  列表」。这样：
  - 被攻破的 CDN **无法伪造撤销**把设备从好补丁上强行踢下来（DoS）——撤销未签名则不认。
  - 私钥泄露时，撤销通道因信任根独立而**仍然可信**（§2.5）。
- **决策点 D4：补丁有效期（无限期 vs 租约 TTL）**。撤销要送达才有效，若攻击者/故障**扣着
  撤销令不发**，设备就一直带着坏补丁。两种应对：
  - **无限期**：补丁一旦生效就长期有效，直到收到取代/撤销。简单；但依赖撤销送达。
  - **租约 TTL**：补丁带一个「有效期」，客户端须在 TTL 内向服务端**续租**（重新确认仍有效），
    否则**自动回退纯基线**（fail-safe）。好处：扣撤销令也会因 TTL 到期而自愈；代价：**长期
    离线设备会自动掉补丁**（可能把已修好的 bug 又暴露出来）。
  > 交用户定。倾向：给关键补丁配一个**较长的** TTL（兼顾自愈与离线容忍），而非纯无限期。

### 5.2 客户端自检崩溃 → 自动回滚（熔断）

对齐「Play 商店预发布崩溃率超阈值自动叫停」的思路，但**没有商店，需自建上报 + 熔断**。分两层：

**(a) 单机 boot-loop 看门狗（本地，不依赖网络）**：

- 应用补丁**前**，写一个 `pending_confirmation(patch_id)` 标记。
- App 启动后到达**健康检查点**（如首帧成功渲染 / 稳定运行 N 秒）→ 把该 patch 标记为
  `confirmed_good`。
- 若在确认前崩溃：下次启动时 Updater 看到「未确认 + 上次异常退出」→ 把该 `patch_id` 加入
  **本地黑名单**、回退纯基线（PRD §5「补丁导致崩溃自动回滚到基线并加入本地黑名单」）。
- **本地黑名单是硬红线**：即便服务端之后又下发同一 `patch_id`，客户端也**拒绝**（§4.1 步骤 5）。

**(b) 机群级熔断（服务端聚合，需上报通道）**：

- 客户端把**应用结果 + 崩溃计数**回传服务端（**匿名聚合计数，不带设备身份**，守 PRD §3 无
  用户系统）。
- 服务端按 `patch_id` 聚合崩溃率；某补丁在其灰度队列里崩溃率超阈值 → **自动 withdraw + 停止
  放量 + 签发撤销令**（§5.1）。
- **决策点 D6**：是否启用 (b)。上报通道虽只回传匿名计数，仍是一条新增数据链路；若产品不接受
  任何回传，可只保留 (a) 单机看门狗（每台设备各自兜底，但服务端「看不到」机群崩溃率、无法
  主动叫停放量）。交用户定。

### 5.3 「运行时状态」与回滚的固有边界（必须讲清楚，不能糊弄）

「补丁需重启生效」意味着补丁不是能随时「卸载」的东西，回滚有一条**无法回避的边界**：

- **回滚只回退代码，回退不了副作用**。补丁生效期间，被改逻辑可能已经往磁盘 / DB / 网络写过
  数据（用「打了补丁的」逻辑写的）。冷启动回退到基线只是把**代码**换回基线，**已经产生的持久化
  副作用不会被撤销**——基线代码之后会读到这些「补丁写下的」数据。
- 这是热修复机制的**固有限制**，不是本方案的缺陷，机制层面无法根治。缓解手段在**补丁作者纪律**
  （避免让补丁写不可逆副作用）+ **灰度限爆炸半径**（§3.2，坏补丁只影响放量队列）+ **熔断快速
  止血**（§5.2），而不在「回滚能自动清数据」——它做不到，也不应假装能做到。
- 已在运行的会话**无法即时回退**（补丁需重启）：服务端下线后，已生效设备要等**下次冷启动**才
  真正回到基线。产品/交互层面须明示这个延迟（对齐 PRD §7）。

## 6. 纵深防御总览（每层独立完整性，不单点信任）

呼应 §0.4 威胁模型，把各威胁与对应的**独立**防线列清楚——任一层被攻破，仍有其它层兜底：

| 威胁 | 独立防线 |
|---|---|
| **CDN / 下发服务器被攻破**，替换补丁产物 | 清单签名（§2）+ 逐产物哈希（§1.1）——端上用**内嵌公钥**验签，服务器控制不了这把钥匙；篡改任一产物都会哈希失配 |
| **传输链路中间人** | TLS（传输层）**叠加**清单签名（应用层）——TLS 被绕过时签名仍拦得住；签名不依赖 TLS 是否可信 |
| **构建产物在服务端被篡改 / 重指向别的 base** | provenance 字段（`target_build_fingerprint` 等）纳入签名覆盖（§1.2），改指向即破坏签名；客户端 fingerprint 校验 fail-closed（§3.3） |
| **攻击者重放旧的合法补丁** | `patch_version` 单调递增 + 客户端只接受不低于当前的版本；本地黑名单挡已知坏补丁 |
| **签名私钥泄露** | 撤销通道信任根独立于被泄露密钥（§2.5）+ 根+子密钥模式（链长 1）可不发版吊销子证书（§2.3）|
| **坏补丁导致崩溃 / 攻击者扣留撤销令** | 单机 boot-loop 看门狗 + 本地黑名单（§5.2a，不依赖网络）+ 可选租约 TTL 自愈（§5.1 D4）|

**贯穿原则**：端上信任根**只有内嵌公钥**。下发通道、传输层、服务端存储都被当作**不可信**处理，
它们的作用是「把字节搬过来」，不是「证明字节可信」——证明可信的唯一依据是签名 + 内嵌公钥。

## 7. 平台差异（下发链路视角）

底层执行差异见 SPEC §7；就**下发链路**而言：

| | iOS | Android（当前主线） |
|---|---|---|
| 补丁包格式 | `payload_type=bytecode`（§1.4） | 同 iOS，`payload_type=bytecode` |
| 签名 / 校验 / 灰度 / 回滚 | **完全一致**（本文全部机制平台无关） | 完全一致 |
| 长期扩展 | 无（W^X 锁死解释器路线，SPEC §7） | 预留 `payload_type=native_so`（SPEC §7.1 三层兜底，暂缓，本文不展开）|

下发链路本身**几乎完全平台无关**——签名、fingerprint 校验、灰度分桶、熔断回滚在两端是同一套。
平台差异只落在补丁**内容**（iOS 恒为字节码；Android 未来可能有原生产物），不落在**下发协议**。

| **D2** | 灰度分桶方式（§3.2） | A 客户端随机分桶 / B 服务端按设备 ID | 倾向 A（守住 PRD §3「无用户系统」） |
| **D3** | 签名信任结构（§2.3） | ~~A 单层 / B 两层~~ → 统一可变长证书链 | ✅ **已决策 2026-07-31**：两种模式（直签=链长 0 / 根+子密钥=链长 1）在同一套校验逻辑下共存，逐 App 于**构建期**选定（`TRUST_CHAIN_LEN` 烧进二进制，非运行时切换）。简单/低价值 App 走直签，复杂/高价值 App 走根+子密钥 |
| **D4** | 补丁有效期（§5.1） | 无限期 / 租约 TTL 自动回退 | 倾向：关键补丁配较长 TTL（兼顾自愈与离线容忍） |
| **D5** | 签名算法族（manifest `sig_alg`） | Ed25519 / ECDSA-P256 / … | 倾向 Ed25519（实现简单、无参数陷阱），交安全评审定 |
| **D6** | 是否启用机群级崩溃熔断上报（§5.2b） | 启用（匿名计数回传）/ 只保留单机看门狗 | 倾向：若产品接受匿名计数回传则启用（能主动叫停放量） |

**明确不作为决策点、直接下结论的安全红线**（§2.2、§3.3、§4.4）：签名验证失败必须拒绝、
fingerprint 不匹配必须拒绝、应用必须全有或全无、坏补丁进本地黑名单、撤销令必须签名、
完备性优先于「看起来生效」。这些没有退让空间。

## 9. 与 Gate 制计划的关系

**本链路的实现排在 iOS Gate 通过之后，但设计（本文）现在就做。** 理由与
`PRODUCTION_LINKER_SPEC.md` §3 一致、也与 `PLAN.md` 开篇原则一致：

- **不单独设一个风险 Gate**。下发/签名/灰度这类外围基础设施的技术信心本就接近 100%
  （PLAN 原则明说「不先搭外围基础设施……那些信心本就接近 100%」），它不是 go/no-go 的
  风险门，不该占一个 Gate 位。
- **设计前置到现在（并行、廉价）**：把设计做出来能**固化 linker 的输出契约**（补丁包该装什么、
  provenance 长什么样），对 Gate2 linker 的接口设计有正反馈，成本只是这份文档。
- **实现留在 M4（iOS 门之后）**：真正建下发服务/CDN/灰度/熔断，属于 `PLAN.md` 正式研发阶段
  已列的「5. Updater」「6. 私有服务端」，对应里程碑 **M4 私有化闭环**。在 iOS W^X go/no-go
  之前不投入这笔工程——否则墙一旦不成立即打水漂（同 PRODUCTION_LINKER_SPEC §3 逻辑）。

详见 `PLAN.md` 新增的「补丁下发链路（设计先行，实现随 M4）」小节。

## 10. 诚实边界（本文没做/暂不展开的部分）

- **未选型任何具体 KMS / 云服务 / CDN 产品**——刻意停在架构层（§0.3），守「可私有化部署」。
  私钥具体怎么冷存、用什么硬件/服务，是实现期决策，不在本文。
- **未展开 Android 原生差分 `.so` 的下发格式**——依赖尚未开建的生产 linker（R1-R9）+ SPEC §7.1
  暂缓项，只在 `payload_type` 留了扩展位。
- **未定 provenance 各字段的精确二进制布局 / 序列化格式**——SPEC §9 也把「provenance 具体格式」
  列为未决项，留到实现期与 linker 输出一起定。
- **回滚回退不了补丁已产生的持久化副作用**（§5.3）——这是机制固有限制，本文只如实标注、
  给缓解方向，不假装能自动清理。
- **多 isolate 下补丁应用/回滚的完备性**——R3.1 诚实边界里已标为「未测的额外维度」；本文的
  §4.4 原子性红线要求「无法完备枚举即判失败」正是为这个未决项兜底，但具体多 isolate 工程
  留到实现期。
