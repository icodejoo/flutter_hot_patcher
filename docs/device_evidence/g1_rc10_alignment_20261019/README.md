# G1 RC10：64 字节来自快照符号填充

2026-10-16 的插入式 `base_ft_link_data` 复核中，两侧的 field `(id, hash)` 集合相同、10,347 个 dispatch 目标同序、链接数据相同，且各自链接前后的 `.text` 相同。待解释的是 `_kDartIsolateSnapshotData` ELF 符号增长：我们 +512 字节，参考 +448 字节。

按快照头部的逻辑长度与 Shorebird 附加块长度重新计量，**两侧链接都增加了 459 字节快照内容，附加块均未增长**。符号大小还含尾部填充：我们的填充由 10 增至 63 字节（+53），参考由 60 降至 49 字节（−11）。因此 `459+53=512`，`459−11=448`，恰好解释符号增长相差 64 字节。两侧原有逻辑长度相差 50 字节，链接后仍相差 50 字节；这使同样的 459 字节增长跨过了不同的符号边界。

复核脚本 `verify.py` 读取四份归档 ELF 和之前的 RC10 语义检查结果，输出 `verification.json` 与输入 SHA-256。它还故意将参考侧链接后的头部长度加一，确认检查会失败。本轮没有修改 SDK 或重新调用参考工具。

这解释了 RC10 的**长度差**，并结合既有目标序列检查排除了已观察到的 dispatch 行为差异；两侧快照内容并未据此证明逐字节相同。G1 的 AOT 基线数据区残差仍待处理。
