# G1 AOT 基线数据区逐字节分解（2026-10-19）

本轮只读复核 2026-10-16 归档的 `hello`、`prog`、`base_dd` 两侧 AOT ELF；校验脚本、输入哈希和两个故意改坏数据的负控制见 `verify.py` 与 `verification.json`。当前 SDK 重跑的三组 AOT 已在[派生输出复核](../g1_aot_derived_20261019/README.md)中证明：相对旧版我方产物仅快照版本哈希变化，指令不变，因此下列旧矩阵的数据区归因仍适用于当前构建。

每组的 VM 和 isolate 序列化快照，我方长度都比参考多 50 字节。我们的 features 串在偏移 194 多出恰好 50 字节的 `shorebird-native-entry-thr-offsets=2312,2320,2328` 标记；在内存中删去这段，并将长度头与版本哈希字段换成参考值后，**六组序列化快照逐字节相同**。这是规范化分析，不建议从 SDK 删除 Thread 布局守卫。

两侧随后的只读数据镜像大小相同，按 8 字节字逐项比较：

| 镜像 | 差异字段 |
| --- | --- |
| VM，三个 fixture | 158 个字段恰好 +4；另有首个对象头的缓存哈希。158 与 VM `Resume` 后的 158 个 stub 数量相同。 |
| isolate，`hello`/`base_dd` | 220 个字段恰好 +4；另有首个对象头的缓存哈希。220 与 `shorebird` JSON 中后移 4 字节的函数数量相同。 |
| isolate，`prog` | 187 个字段恰好 +4；另有首个对象头的缓存哈希。187 与后移函数数量相同。 |

首个对象是 `OneByteString`（本 SDK 的 class id 94）；对象头高 32 位是缓存哈希。校验脚本按 SDK 的 `StringHasher` 算法，从两侧各自的字符串字节重新计算哈希，六组均与各自对象头完全一致。字符串内容中的上述 +4 偏移字足以使缓存哈希不同，因此这不是另一个未解的随机字段。两侧数据符号总长相差 64 字节，其中序列化快照增加 50 字节、快照与数据镜像间的 64 字节对齐填充增加 14 字节；镜像自身长度相同。

这将旧分类里的 AOT 数据区 D1 从「剩余差异」变为可逐字节核对的 RC1（版本哈希）、RC2（features 标记及填充）、RC3（Resume 后位置 +4 及字符串缓存哈希连带变化）。它不改变此前保留安全修复的决定，也不自动完成 G1 的全部验收：RC9 第一轮 key map 诊断、JIT 跨 Thread 布局加载保护与整体接受判据仍须单独处理。
