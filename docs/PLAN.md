# PLAN — flutter_hot_patcher

分阶段实施计划（Gate 制）/ Phased Implementation Plan
版本 v0.1 · 2026-07-29

---

## 原则

**先攻最高风险假设**（de-risk the riskiest first）。不先搭外围基础设施（下发服务器、CDN、灰度），
那些信心本就接近 100%，先做只是推迟面对真正的风险。核心风险按 X→Y 顺序验证，每个 Gate 有
明确的**继续/放弃判据**，用最小代价尽早杀死不可行方案。

当前起点：**Gate 1 — 难点 X（混合执行 ABI）**。

> **2026-07-31 更新**：Gate 1 已在桌面 x64、Android arm64 真机、iOS 真机三个平台全部
> PASS（详见 `spikes/gate1_mixed_execution/GATE1_REPORT.md` §14）——iOS W^X 真机复验
> 通过：V1 不可行但非必需，V2 完全可行。当前进入 Gate 2 生产 linker 阶段。

## Gate 1 — 「替换既有函数」验证（约 2 人周 ~ 1 人月）

### 靶心更正（重要）
**不是验证"互操作"**——官方 dynamic modules 本就支持"新增字节码函数 ↔ AOT 互调"，验证互操作会
**假阳性通过、证明不了核心命题**。真正无公开先例、决定生死的假设是**替换**：让基线里**已优化编译
的既有调用点，运行时走到字节码版本的新函数**。Gate 1 必须打这个靶心，同时覆盖 X 的 ABI（异常/GC）。

### 平台策略更正
**先桌面 arm64（macOS/Linux）预验证，不从 iOS 真机起步**——桌面迭代快一个量级，ABI 结论可迁移；
iOS 真机作为预验证通过后的最终复验（W^X + 无 JIT 是 iOS 特有约束，桌面通过 ≠ iOS 通过）。

### 前置准备
1. 拉取 dart-lang/sdk，用 `--dart-dynamic-modules` 构建 `gen_snapshot` + `dartaotruntime` + `dart2bytecode`。
2. 跑通官方 `pkg/dynamic_modules/example`，确认工具链可用（这一步顺带验证了"新增+互操作"，作为基线能力）。

### 验证用例（核心：替换）
- **V1 静态直调替换**：函数 `f` 被 `g` 调用，`@pragma('vm:never-inline')` 禁内联；AOT 编译后用
  `dart2bytecode` 生成**行为不同**的 `f'`；启动期把 `f` 的入口切到解释器的 `f'`。断言 **`g` 的调用
  确实落进 `f'`（行为变化可观测）**。这是最硬、最能证伪整个方案的用例，**第一个做**。
- **V2 三种调用形态**：分别覆盖静态直调、虚调用、闭包调用，记录**哪些入口可重定向、哪些必须连带
  失效**——直接产出"传递闭包边界"的一手数据。
- **V3 异常穿透**：在 `f'`（解释帧）抛异常，穿透回 `g`（AOT 帧）正确捕获；`finally`/`rethrow` 正确。
- **V4 GC 正确性**：在 `f'` 内触发 GC，混合栈两种帧的对象引用都被正确扫描，无误回收/崩溃。
- **V5 稳定性**：上述高频循环压测，无泄漏/偶发崩溃。

### 通过 / 放弃判据
- ✅ **通过**：V1（替换可观测生效）+ V3/V4（异常/GC 正确）稳定跑通，且 V2 能清晰划出可重定向/
  必失效边界 → 进入 Gate 2。
- ❌ **放弃**：V1 无法让既有调用点走到 `f'`，或 GC/异常在混合栈下崩溃且 2 人周内无解 →
  **iOS 自研路线终止**，回落到「Android 自研整包替换 + iOS 加急审核/购买 Shorebird」。

### 产出
- `spikes/gate1_mixed_execution/` 可复现实验工程 + 结论文档（V1 替换是否生效、V2 三形态可重定向性
  矩阵、异常/GC 关键发现、入口切换的实现手法）。

## Gate 2 — 逐函数替换 + 编译期约束验证（约 1 ~ 2 人月）

### 前置
Gate 1 通过。

### 目标
验证难点 Y（通用版，任意 Dart 代码）：基线全优化编译下，linker 能否正确识别"受影响传递闭包"
并转解释执行，使补丁行为与完整重编译的新版本一致，且解释比例导致的性能下降可接受。

> 策略为 Shorebird 式"全程序 diff + 智能 linker + 基线正常优化"，**不**采用收窄的"编译期圈定
> 可 patch 区域"。因此本 Gate 直接面对全场最硬、无公开先例的问题，是真正的可行性判定。

### 验证用例
- **V6 去虚化路由**：替换一个被去虚化直接调用的函数，验证 linker 能识别并让调用点正确走到新版本（转解释）。
- **V7 内联级联**：替换一个被多处内联的函数，验证所有内联调用者被正确纳入解释、行为正确。
- **V8 真实修复场景**：构造若干真实改动（改函数体、改被多处调用的函数、改含分支的逻辑），补丁后行为与完整重编译版完全一致。
- **V9 类字段布局变更（放开任意 Dart 代码后的关键新增用例）**：给一个类增删字段，验证所有访问该类字段的代码被正确处理，无内存错乱/读到错误偏移。**这是最可能推翻方案的用例，务必优先做。**
- **V10 影响范围与性能**：测量典型改动下"受影响传递闭包"的规模，及其导致的解释比例与性能下降幅度（**关键决策数据**）。

### 通过 / 放弃判据
- ✅ **通过**：V6–V9 正确 **且** V10 性能下降产品可接受 → 可行性确认，进入正式研发。
- ❌ **放弃**：V9（字段布局）无法可靠解决，或影响范围/解释比例失控致性能不可接受，或替换频繁出现难以预测的错误 → 该墙对我方不成立，放弃 iOS 自研。

### 产出
- `spikes/gate2_linker/` 实验工程 + 结论文档（含 V9 性能/体积实测数字，供产品决策）。

## 正式研发阶段（Gate 1+2 均通过后，团队级、按季度~年）

> 仅在两个 Gate 均通过后启动。以下为方向性拆解，细化留到进入本阶段时。

1. **Linker 工程化**：Kernel 层 `CanonicalName` diff + 字节比对二次确认 + 保守策略 + 影响范围分析。
2. **编译期约束工程化**：把 Gate 2 验证的关闭优化改造，做成可配置、最小侵入的 AOT 编译器 pass。
3. **补丁流水线**：`dart2bytecode` 打包 + 签名 + provenance（SDK 版本/基线校验和绑定）。设计见 `PATCH_DELIVERY_SPEC.md` §1/§2。
4. **运行时集成**：基于官方 Engine 自写生命周期钩子（对齐 Shorebird 的能力定位）；集成官方解释器。
5. **Updater**：对齐 `updater`(Rust) 的能力范围，自行设计实现下载/校验/回滚/黑名单。设计见 `PATCH_DELIVERY_SPEC.md` §4/§5。
6. **私有服务端**：补丁管理后台 + 下发 API + CDN + 灰度控制。设计见 `PATCH_DELIVERY_SPEC.md` §3/§5。
7. **差分等价测试台**：同一测试集在「完整重编译新版本」与「打补丁的旧版本」上跑，断言行为一致——发布前拦截判错。
8. **Android 线**：可与 iOS 解耦并行，用整包 .so 替换先行落地（信心 ~95%，不依赖上述核心）。
9. **VM/Engine fork 维护机制**：锁定单一 Flutter 版本/发布周期，建立 rebase + 全量回归流程。

## 补丁下发链路（设计先行，实现随 M4）

补丁生成 → 签名 → 下发 → 客户端应用 → 回滚 的全链路架构，完整设计见
`PATCH_DELIVERY_SPEC.md`。它对应上面正式研发阶段的第 3/5/6 项与里程碑 **M4 私有化闭环**。
关于「为什么这样排期」，明确如下：

- **不单独设风险 Gate**。它是外围基础设施（下发/签名/灰度/熔断），技术信心本就接近 100%
  ——正是本计划开篇「不先搭外围基础设施，那些信心本就接近 100%，先做只是推迟面对真正风险」
  点名的那类东西。它不是 go/no-go 的生死门，不占 Gate 位，也不与 Gate1/Gate2 并列成第三个 Gate。
- **设计前置到现在（并行、廉价）**：把设计做出来能**固化 linker 的输出契约**（补丁包装什么、
  provenance 长什么样、版本指纹怎么绑），对 Gate2 linker 的接口设计有正反馈，成本只是一份文档
  （`PATCH_DELIVERY_SPEC.md` 已完成）。这一步现在做，不依赖 iOS/Android 底层验证结果。
- **实现留在 M4（iOS 门之后）**：真正建下发服务/CDN/灰度/熔断，与 `PRODUCTION_LINKER_SPEC.md`
  §3 同理——在 iOS W^X go/no-go 之前不投入这笔工程，否则墙一旦不成立即打水漂。
- **决策点待拍板**：`PATCH_DELIVERY_SPEC.md` §8 汇总了 6 个需用户拍板的方向选择（轮询vs推送、
  灰度分桶方式、签名信任结构等），其中 **D3 签名信任结构建议最先定**（一旦发版就固化进二进制、
  且直接决定私钥泄露的恢复能力）。
