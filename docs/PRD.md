# PRD — flutter_hot_patcher

产品需求文档 / Product Requirements Document
版本 v0.1 · 2026-07-29

---

## 1. 背景与问题

Flutter App 的 Bug 修复依赖应用商店发版。iOS 侧尤其受制于审核周期（常规审核数小时到数天），
紧急故障无法即时修复。业界唯一成熟的 Flutter iOS 热更方案 Shorebird 存在三个不可接受的约束：

1. **闭源**：核心解释器与差分算法（linker）、服务端均不开源。
2. **不支持私有化部署**：官方明确无 on-prem/self-host 计划，数据必须经其云服务（含数据出境）。
3. **ToS 禁止自托管商用**：许可证只授权"用其服务构建并分发自有 App"，不允许分发/衍生其 Services 任何部分。

同时，开源替代品（flutter_patcher 等）仅支持 Android 整包 `.so` 替换：无差分（补丁体积大）、无 iOS。

## 2. 目标

构建一套**数据自主可控、可私有化部署**的 Flutter 热更新能力：

- **P0**：iOS 端可对已发布 App 做**任意 Dart 代码**的热更，无需过审，符合 Apple 审核政策（解释型代码，Guideline 3.3.1b）。
- **P0**：全链路私有部署——补丁生成、签名、下发、回滚均在自有基础设施内完成，不依赖任何第三方 SaaS。
- **P1**：Android 端热更（技术上更简单，可用整包 .so 替换先行落地）。
- **P2**：差分补丁（小体积），逐函数级别，尽量逼近但**不强求**对标 Shorebird 的 98% 原生复用率。
- **P3（长期方向，暂缓）**：Android 差分补丁原生化——不回落解释器，直接把差分闭包编译成原生
  机器码、用 Gate1 V1/V2 已验证的重定向机制指向新下发的原生代码，兼得"体积小"与"无解释损耗"；
  依赖与 iOS 同等成熟度的生产 linker（R1-R9），排在 iOS Gate 通过之后，见 `SPEC.md` §7.1。

## 3. 非目标（明确不做）

- **不做通用动态化框架**：不追求"任意加载第三方模块"，只服务自有 App 的"新旧版本差分"这一封闭场景。
- **不支持 assets 静态资源与 native 热更**：图片/字体/json 等 assets、`.so`/OC/Swift/Kotlin 等 native 层不在范围内（见 §6）。
- **不使用任何第三方闭源产物**：全部基于官方开源代码（Dart/Flutter BSD 协议）自研。

## 4. 目标用户与场景

- **用户**：自有 App 的研发团队。
- **核心场景**：生产环境紧急 Bug（崩溃、逻辑错误、文案/规则错误），需在小时级甚至分钟级修复，且不希望走商店审核。
- **可接受的代价**：补丁生效期间，被改动的函数走解释执行、性能下降；此状态持续到下一次正式发版替换掉补丁为止（见 §7）。

## 5. 成功标准

| 指标 | P0 目标 |
|---|---|
| iOS 补丁生效 | 已发布 App 无需过审即可应用任意 Dart 代码补丁，行为正确 |
| 合规性 | 通过 App Store 审核，不因动态代码被拒 |
| 私有化 | 补丁生成/签名/下发/回滚全在自有基础设施完成 |
| 安全兜底 | 补丁导致崩溃时自动回滚到基线版本，并加入本地黑名单 |
| 正确性 | 差分等价测试台通过率 100%（判错必须在发布前拦截，不允许漏到线上） |

## 6. 补丁能力边界

补丁**允许**：修改**任意 Dart 代码**——函数体逻辑、类结构、字段、常量/静态初始化、
Widget 树逻辑、新增/删除类与方法等，均在范围内（对标 Shorebird 的能力覆盖）。

补丁**不支持**（超出范围，需走正式发版）：

- **assets 静态资源**：图片、字体、json、`.arb` 等随包打进 assets 的资源文件。
- **native 代码**：`.so`/Objective-C/Swift/Kotlin 等非 Dart 层，天然无法通过 Dart 字节码热更。
- **依赖版本/native 插件变更**：引入新的 native 依赖或改动其 native 部分。

> **重要权衡（相对 v0.1 的变更）**：放开到"任意 Dart 代码"意味着放弃了"收窄补丁能力"这个
> 提升信心的核心杠杆，目标回到对标 Shorebird 的通用版本。这会**显著抬高难点 Y 的难度**，
> 主要新增两类硬问题：(1) 改类字段布局时，端上已编译的 AOT 代码按固定偏移访问字段，与补丁的
> 新布局不一致会导致内存错乱；(2) 补丁可能触及全程序任意函数，编译期约束若要覆盖"任意可 patch"
> 就会退化成"暴露整个 App"，摧毁 tree-shaking/全局优化（Dart 官方 Dynamic Modules 判定此路
> 生产不可行）。因此技术策略须改走 Shorebird 式"全程序 diff + 智能 linker + 基线正常优化编译"
> 路线，而非"编译期圈定可 patch 区域"路线——这正是全场无公开先例的最硬部分。详见 SPEC §3/§4。
> 生产级信心相应从"收窄版可达 50%+"回落到"通用版 ~25%"。

## 7. 已知约束与风险（来自前期调研）

- **iOS 无 JIT**：平台 W^X + 代码签名限制，补丁只能纯解释执行，性能提升手段（分层 JIT）在 iOS 上被禁止。换实现语言（Rust 等）无法改变此约束。
- **性能断崖**：补丁生效期间，受影响函数解释执行慢 10–100×。轻量 UI 场景可接受，逻辑/计算密集场景会明显掉帧。补丁状态持续到正式发版，**不是"重启即恢复"**。
- **核心技术墙**：逐函数替换已有代码时，AOT 编译器的去虚化/内联/树摇（封闭世界假设）会导致调用方跳不到新函数；支持任意 Dart 代码后还叠加"类字段布局变更导致 AOT 代码按旧偏移访问内存错乱"的问题。这是全场唯一无公开先例的难点。因目标为通用版（任意 Dart 代码），须走 Shorebird 式"全程序 diff + 智能 linker + 基线正常优化"路线（见 SPEC §3/§4），Dart 官方 Dynamic Modules 判定此通用问题"怀疑生产不可行"，故此为最大风险点。
- **长期维护成本**：需维护 Dart VM + Engine 的 fork，每次跟随 Flutter 升级都要 rebase + 回归。这是本方案的持续性负担，也是 Shorebird 真正的护城河。
- **补丁需重启（冷启动）生效**：运行时不做热切换，用户需重启 App 补丁才生效，且生效后一直持续到下次正式发版。产品/交互设计须明示。
- **字节码特性覆盖未知**：`dart2bytecode`/解释器为实验特性，对 async/await、FFI callback、部分 intrinsic 的支持未验证；整个 Flutter framework 能否全量降到字节码是未知数——若不能，补丁触及这些路径时无法解释执行。**此为 Gate 2 的重大未知项。**
- **符号绑定无现成答案**：补丁字节码引用基线快照内实体的绑定机制，官方仅为"新增"设计，"替换"场景需自研，是 linker 未解的另一半。

## 8. 决策门（Gate 制）

本项目不一次性投入，按风险从高到低分 Gate 验证，每个 Gate 有明确的"继续/放弃"判据（见 PLAN）：

- **Gate 1**：难点 X（混合执行 ABI）能否跑通 —— 生死判定，先做。
- **Gate 2**：难点 Y（逐函数替换 + 编译期约束）能否正确生效且性能回退可接受。
- Gate 全过 → 进入正式研发；任一 Gate 否决 → 回落到"Android 自研 + iOS 加急审核/买 Shorebird"备选方案。

## 9. 备选方案（Gate 否决时的回落路径）

- **Android 自研整包 .so 替换**（信心 ~95%，无需本方案核心）+ **iOS 苹果加急审核**（24–48h，零成本零风险）。
- 或 iOS 直接购买 Shorebird 云服务（接受第三方依赖与数据出境）。
