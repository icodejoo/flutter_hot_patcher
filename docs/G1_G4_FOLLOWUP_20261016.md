## G4 修复与分层结果

### 签名公钥编码

原 CLI 输出 DER SPKI 公钥，参考 updater 的 `ring::RSA_PKCS1_2048_8192_SHA256` 验证器要求 DER PKCS#1。用同一密钥、消息和签名调用参考 `signing.rs`：SPKI 被拒绝，PKCS#1 通过；本轮 2048 位测试密钥的两种 DER 分别为 294 和 270 字节。

密钥生成现在输出 PKCS#1 的 base64 wire 表示，PEM 仍使用正常的 `PUBLIC KEY` 表示。读取旧 SPKI 缓存时仅转换返回值，不改缓存或私钥。`verify` 严格检查设备支持的 RSA 位数、DER 编码和 base64，并对坏公钥、坏签名返回失败。已嵌入旧 SPKI 的应用需要用同一密钥的 PKCS#1 表示重新构建。

17 项签名测试通过，包含真实参考 Rust 验证函数的正反控制；参考 updater 的 249 项宿主测试也通过。该 oracle 使用公开 updater 提交 `1f85c4ab1ee5b540269b9859c75e1bffbb9050c7` 的源码，不等同于已装机 iOS 二进制的完整更新链路。

证据：[修复前独立验签](device_evidence/g4_20261016_signature_encoding_before.json)、[17 项测试](device_evidence/g4_20261016_signing_tests.log)、[249 项宿主测试](device_evidence/g4_20261016_updater_host_tests.log)。

### 直接 ELF 加载

修复前，命令行外层会拒绝坏 ELF 魔数，而直接调用 `Dart_LoadELF` 会打印 `LOAD_OK`；文件截断到 10% 和 50% 时，直接入口触发 `SIGBUS`。这说明只测试命令行外层会漏掉真实加载器问题。

加载器现在核对 ELF 魔数、实际文件长度、映射范围、segment 文件大小和内存大小，以及地址计算溢出。修复后的 18 组检查包含正常对照，直接入口没有崩溃，截断文件会干净拒绝；9 个正常 AOT 程序均完成编译、加载与执行。探针链接真实 SDK loader，不使用另写的解析器代替它。

双方命令行有 17 组处置相同、1 组不同：`segment_outside_file` 被我们拒绝、被参考接受，登记为 `G4-20261016-01`；后续 21 次边界对照证明原变异同时违反文件范围与文件大小≤内存大小的约束，已按限定例外处理，保留严格拒绝。详见 [处置记录](G4_RESOLUTION_20261016.md)。原 14 组命令行对拍一致，也没有参考命令行崩溃。

### 参考分析器为何崩溃

> 2026-10-16 复核订正：本节原写「崩溃栈将 `SIGBUS` 定位到 `DDTableLinkInfo::ReadFromStream`」，又写损坏输入「没有在读取和分配前得到充分校验」，两句都过宽。原归档只有 2 份 SIGBUS 栈，都是表类输入；四次 SIGBUS 的栈并不全在 `ReadFromStream`。下文按七份崩溃报告逐一核对后改写，审定摘要见 [G4 崩溃报告审定摘要](device_evidence/g4_review_20261016/summary.md)。

本轮五类损坏输入中，空文件重复三次：参考出现四次 `SIGBUS`、三次 `SIGABRT`，我们七次均干净拒绝；双方有效输入均成功，产出的 mapping 相同。

七次崩溃按栈分为三类：

- **表输入 SIGBUS**：`table_count`、`table_trunc1`、`table_trunc2000` 三次，栈上第一个 Dart 帧都是 `DDTableLinkInfo::ReadFromStream +436`，调用方为 `Dart_ComputeDDSlotMapping`。
- **caller links SIGBUS**：`links_flip20000` 一次，栈顶为 `Dart_ComputeDDSlotMapping +732`，崩溃时栈上没有 `ReadFromStream` 帧。这只说明崩溃时不在该函数内，不说明它从未被调用。该变异把 offset 20000 的 `0xa8` 改为 `0xaa`。按公开 datastream 格式，这是索引 340（从 0 计数）的 caller link 的哈希长度前缀，40 变成 42，最高位（终止位）不变。按同一格式继续解析，从索引 340（从 0 计数）的起错位，到索引 349（从 0 计数）的记录读到文件末尾，与我们的诊断 `truncated at link 349 of 930` 一致。参考端崩溃时正在读哪个字段，没有确认。
- **空输入 SIGABRT**：三次都经 `vector<DDEntry>::reserve`，由 `ReadFromStream +164` 调用。参考端 stderr 写明 `length_error` 或 `bad_alloc` was thrown in `-fno-exceptions` mode。今天四批运行共 12 次相同的空输入，7 次 `length_error`、5 次 `bad_alloc`。实际解码出的计数和请求的分配量没有保存，「读到无效字节后请求过大分配」仍是推断。

可复核的事实是：这些坏输入使参考端越界读取或中止，没有干净拒绝。不能据此断言它的解析器在任何位置都不做边界检查。这些结果发生在宿主分析器的 DD 解析阶段，不是设备更新器的回落行为。处置差异登记为 `G4-20261016-02`，保留差异，不将崩溃与正常报错算作一致；后续已补齐七次崩溃的输入/PID/IPS 绑定，按限定的干净拒绝例外验收，见 [处置记录](G4_RESOLUTION_20261016.md)。

各批对拍都只留下 5 份崩溃报告，`table_trunc2000` 和 `links_flip20000` 的报告来自 16:11 的两次单独补跑，补跑输入没有另存。原归档的五份栈来自 14:27 批次，运行记录来自 14:51 批次，两者不是同一批。

证据：[逐次命令与输入哈希](device_evidence/g4_20261016_dd_inputs.json)、[去除无关个人信息后的符号化崩溃栈](device_evidence/g4_20261016_dd_crash_stacks.json)（14:27 批次，仅五份）、[七份栈与只读复核](device_evidence/g4_review_20261016/verification.json)。
