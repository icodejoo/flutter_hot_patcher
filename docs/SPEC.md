## 0. 阅读前提

本文承接前期调研结论。关键事实（均有源码/官方文档佐证）：

- Dart AOT snapshot 采用 clustered serialization（`runtime/vm/app_snapshot.cc`，48 种 `XxxSerializationCluster`），对象引用是全局 ref 数组的逻辑下标，顺序随堆遍历（Trace）而非源码声明。
- Kernel（`.dill`）是 AOT 之前的 AST 中间表示，每个实体带 `CanonicalName`（库 URI→类→成员的稳定路径标识），格式见 `pkg/kernel/binary.md`。
- Dart 官方字节码解释器 `runtime/vm/interpreter.cc` 现存于主干，`--dart-dynamic-modules` 编译开关开启；配套 `dart2bytecode` 编译器可将 Dart 编译为字节码。均 BSD。
- Shorebird 的 Engine 集成层代码公开可见；其 Dart VM fork（含 linker + 解释器改造）闭源，本项目不涉及、不使用。
- Shorebird 运行时更新器 `updater`（Rust）开源，本项目 Updater 对齐其能力范围（下载/校验/回滚/黑名单）自行设计实现。

## 2. 组件清单与技术来源

| 组件 | 来源策略 | 说明 |
|---|---|---|
| Updater（下载/校验/回滚） | **对齐 `updater`(Rust) 能力范围，自实现** | 相对独立，唯一"接近拿来即用"的开源件 |
| Engine 集成/胶水层 | **基于官方 Flutter Engine 自写，对齐 Shorebird 的能力定位** | 不 fork Shorebird 引擎——其接口对接自家闭源 VM，与我方核心接口对不上 |
| 字节码解释器 | **用官方 `interpreter.cc`** | `--dart-dynamic-modules` 开启，BSD |
| 字节码编译器 | **用官方 `dart2bytecode`** | BSD |
| **Linker（逐函数替换 + 编译期约束）** | **纯自研，无可 fork 对象** | 本项目唯一的核心黑盒，火力集中于此 |

> 结论：不 fork Shorebird 的产物，而是 fork 官方 Dart/Flutter + 对齐 Shorebird 已开源组件的能力范围 + 自研核心难点。接口自洽。

## 3. 核心难点分解

自研核心（linker）实为两个独立难点，X 是 Y 的前置：

### 难点 X — 混合执行 ABI（运行时机制）

解释执行的函数与 AOT 机器码函数能否安全互操作：
- AOT → 解释器 调用
- 解释器 → AOT 回调
- 异常跨两种栈帧正确抛出/捕获
- GC 时两种栈帧都被正确扫描（stackmap），无悬垂/误回收

这是运行时问题。**因 `interpreter.cc` 现成，验证成本已大幅降低**，是第一个要冲的 Gate。

### 难点 Y — 逐函数替换而不破坏全局优化（编译期语义 + 内存布局）

> 因 PRD §6 放开到"任意 Dart 代码"，本难点为通用版，采用 Shorebird 式"全程序 diff + 智能
> linker + 基线正常优化"路线（**不**走"编译期圈定可 patch 区域"的收窄路线——后者覆盖任意
> patch 会退化成暴露整个 App、摧毁全局优化，Dart 官方判定生产不可行）。

基线 App 正常全优化编译；补丁版也完整编译；linker 对比两份完整产物，逐函数决定复用/替换。
需解决的硬问题：

- **去虚化**：调用点被硬编码为直接跳转 → 若目标函数被替换，调用方仍跳旧逻辑。需 linker 在替换
  一个函数时，识别并连带处理所有对它做过去虚化直接调用的调用点（这些调用方也须走解释路径）。
- **内联**：被改函数已内联进调用者 → 无独立入口。凡内联了被改函数的调用者，整体判为"已变、走解释"。
- **树摇**：补丁需调用的函数若在基线被删 → 端上不存在。需检测并将其一并纳入补丁字节码携带。
- **类字段布局变更**：改动类字段会改变对象内存布局。**在正确模型下（补丁即权威程序、重启生效，
  无旧布局活对象残留）**，此问题降级——布局变更类的相关代码因机器码字节不等价而自动不复用、转解释，
  不再是"内存错乱"，而是"解释比例上升"（并入下方性能问题）。但需配合 §4.3 的 cid 稳定化，
  避免增删类引起 cid 漂移把大片无关代码也拖成不等价。

核心机制（见 §5 正确模型）：基线降级为机器码池，linker 按逐字节等价判定每个函数入口指向基线机器码
或解释器 stub；**保守优先**——不确定一律转解释（宁慢不崩）。代价是解释比例上升、性能下降；
**比例失控是主要失败模式**，Gate 2 需实测。

## 4. Linker 设计（难点 Y 的实现纲要，Gate 2 后细化）

Linker 的输出不是"变化函数列表"，而是**新程序的完整入口表**（每个函数入口→基线机器码 或 解释器 stub）+ 需携带的字节码。步骤：

1. **函数身份对齐**：用 Kernel 层 `CanonicalName` 匹配新旧版本同一函数（已解决，官方机制，确定性）。
2. **逐字节等价判定**：对齐后，比较新旧函数编译出的机器码是否**逐字节等价**、且其内部直调/内联目标仍有效。等价 → 入口指回基线机器码；否则 → 入口指向解释器 stub。**保守优先**：任何不确定一律判为不等价、走解释。
3. **class id 稳定化（关键）**：增删类会使 cid 全局漂移，导致大片无关代码字节不等价、解释比例爆炸。Linker 必须做 cid 稳定映射，让未变类保持原 cid。
4. **传递闭包**：被改函数 F → 直调/内联 F 的调用者机器码不再等价 → 也转解释 → 向上蔓延，止于虚调用点（dispatch table 可重定向）。闭包有界但可能大，直接影响性能（Gate 2 实测）。
5. **符号绑定（linker 的另一半，官方无现成答案）**：补丁字节码如何绑定引用到基线 AOT 快照内的实体（类、函数、常量）。官方 dynamic modules 只为"新增"设计，"替换"场景的符号绑定需自研。
6. **补丁打包**：字节码（`dart2bytecode`）+ 入口表 + 元数据（provenance：SDK 版本、基线校验和、cid 映射），签名后成补丁包。
7. **diff 工具骨架**：参考 `pkg/vm_snapshot_analysis` 的 `ProgramInfo`（库→类→方法分层模型）。

## 5. 运行时模型（核心架构，难点 X 的正确前提）

> **关键更正（v0.1 曾写错）**：不是"基线快照原样加载 + 补丁字节码叠上去、VM 逐调用决定走哪边"
> 的**补丁叠加模型**。在补丁叠加模型下，基线里被去虚化/内联/pc-relative 直调的调用点固化在
> iOS 只读签名代码段中不可改写，解释器版新函数根本没有入口被调用到——该模型是错的。

正确模型是**"补丁即权威程序，基线降级为已签名机器码池"**：

1. **补丁是完整程序的元数据**：新版本的类表、对象池、dispatch table、函数入口表全部来自补丁
   （这些是**数据**，可下发、可加载）。补丁定义了"这个程序长什么样、每个函数入口指向哪里"。
2. **基线快照降级为一个只读的、已签名的机器码池**：不再是"权威程序"，只是一堆可复用的机器码页。
3. **Linker（构建期）决定每个函数入口指向哪里**：
   - 若新程序某函数的机器码与基线**逐字节等价**、且其内部直调目标仍有效 → 入口指回基线代码页（走原生全速）。
   - 否则（被改函数，及内联/直调过它的调用者）→ 入口指向**解释器 stub**，执行补丁携带的字节码。
4. **重定向不靠改机器码**：靠新程序自身的入口表与调度结构（补丁提供的数据）。虚调用走
   dispatch table 天然可重定向；静态直调/内联是"直调链失效向上蔓延"，形成有界的传递闭包。
5. **传递闭包是替换的自然结果**：改一个函数 → 直调它的、内联它的调用者的机器码不再字节等价 →
   它们也转解释 → 继续向上，直到遇到可重定向的边界（虚调用点）为止。

### 运行时启动流程

对齐 Shorebird 已开源引擎的生命周期插入点设计：

1. 引擎启动时，Updater 检查 next-boot 补丁路径。
2. 基线机器码池（iOS 上通过类似 `SnapshotsDataHandle` 的机制暴露四块 blob）与补丁数据同时就绪。
3. 按补丁提供的入口表建立程序视图：等价函数入口→基线机器码，其余→解释器 stub。
4. 崩溃探测：补丁生效后若启动/运行崩溃，标记坏补丁、加黑名单、下次启动回滚基线。
5. **补丁需重启（冷启动）生效**——运行时不做热切换，见 PRD §7。

## 6. 安全与合规

- **合规**：iOS 仅下发**解释型字节码**（非机器码），符合 Guideline 3.3.1b；不生成/执行新机器码，不绕过签名沙箱。
- **补丁签名**：补丁包用自有私钥签名，端上用内置公钥校验（参考 `updater` 的 `patch_public_key` / `patch_verification` 机制）。
- **provenance**：补丁绑定基线 App 的 SDK 版本 + 校验和，版本不匹配拒绝加载（Dart 字节码无稳定 ABI，必须校验）。
- **传输**：TLS。
- **纵深防御**：编译期约束（降误判）→ 保守策略（宁慢不崩）→ 崩溃回滚（兜底）→ 灰度发布（限爆炸半径）→ 发布前差分等价测试（最后一关）。

## 7. 平台差异

| | iOS | Android |
|---|---|---|
| 执行方式 | 混合执行（AOT + 解释器），受 W^X 限制只能解释 | 可整包 .so 替换（原生机器码，无解释、无性能损失） |
| 难度 | 高（难点 X + Y） | 低（可参考 flutter_patcher 先行落地） |
| 落地顺序 | Gate 验证通过后 | 可与 iOS 解耦，独立先做 |

> Android 若采用整包替换，不需要本 SPEC 的 linker/解释器，信心 ~95%。iOS 才是核心难点所在。

### 7.1 Android 长期方向：三层兜底（2026-07-31 记录，暂缓，待 iOS Gate 通过后再深入）

Android 不强制 W^X（`spikes/gate2_linker/research_machinecode_route.md` §2.1、Gate1b 实测），
理论上差分闭包的重定向目标（V1/V2 机制）不必回落解释器，可以指向**新下发的、编译好的原生
机器码**（小体积差分 .so + `dlopen`）——同时拿到"补丁体积小"和"无解释器性能损耗"，比 iOS
的解释器路线更优、也比整包 `.so` 替换更省流量。三种手段按优先级构成兜底链：

1. **差分 + 原生重定向**（最优，体积小 + 原生速度）——需要与 iOS 同等成熟度的 R1-R9 生产
   linker（闭包正确性问题与目标是解释还是原生**无关，是同一个硬骨头**），外加 Android 特有的
   "差分 .so 与运行中的基线二进制正确链接"工程（新问题，未评估工作量）。
2. **差分 + 解释执行**（当前 Gate1/Gate2 主线，体积小，但补丁函数性能有损耗）。
3. **整包 `.so` 替换**（PRD P1，当前的 Android 保底档，最简单最安全，体积大）。

**明确暂缓的原因**：第 1 层依赖的生产 linker（R1-R9）尚未开建，且排在 iOS W^X go/no-go 之后
（`PRODUCTION_LINKER_SPEC.md` §3）；在此之前，Android 侧仍以整包 `.so` 替换（第 3 层）先行
落地，不因这个长期方向的存在而推迟。这条记录只是把"生产 linker 建成后，Android 该往哪个
方向升级"这件事先定下来，避免以后重新讨论一遍。

## 8. 长期维护约定

Dart VM fork + Engine fork 需跟随 Flutter 官方版本 rebase。约定：**每个 App 发布周期锁定单一
Flutter/引擎版本构建**，不追求通用兼容矩阵，以控制维护成本。升级时重新构建 + 全量回归。

## 9. 未决问题与已知风险（待 Gate 验证或后续细化）

- **符号绑定**：补丁字节码引用基线 AOT 快照内实体的绑定机制——官方仅为"新增"设计，"替换"无现成答案，是 linker 未解的另一半。
- **字节码特性覆盖**：`dart2bytecode`/解释器是实验特性，对 async/await、FFI callback、部分 intrinsic 的覆盖未验证；**整个 Flutter framework 能否全量降到字节码是未知数**（若某些框架代码无法字节码化，被改函数一旦触及这些路径就无法解释执行）。
- **class id 漂移**：增删类导致 cid 全局漂移 → 大片无关代码字节不等价 → 解释比例爆炸。需 cid 稳定化（见 §4.3）。
- **diff 稳定性 vs 小体积**：clustered serialization 引用顺序随堆遍历漂移（§0），若补丁携带完整数据快照，diff 不稳定，威胁 P2 小体积目标。
- **传递闭包规模**：多层内联下闭包可能很大，解释比例失控是主要性能失败模式（Gate 2 实测）。
- **性能/体积**：解释比例导致的性能下降幅度（Gate 2 关键决策数据）。
- **provenance/版本校验**的具体格式。
