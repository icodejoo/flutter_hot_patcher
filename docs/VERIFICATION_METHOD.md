# 核验方法：怎么读一份别人交上来的结论

2026-09-16 立。写它的直接原因是那一天 16 次委派里，**我自己两次把「核过一半」当成了「结论成立」**，
两次都由敌意证伪 pass 抓到，而不是由我的复核抓到。

CLAUDE.md 里那本「37 种假绿」记的是**判据怎么坏**。
这份文档记的是**读判据的人怎么坏** —— 两者是不同的失效面，后者以前没人写下来。

---

## 0. 一句话：所有这些错误是同一个形状

> **信心从「我能便宜地核对的那条主张」漏到了「我核不了的那条主张」上。**

而这两类主张不是随机分布的：**能便宜核对的那条，往往正是外围的那条**。
它便宜，是因为它不承重。

三个当天的实例，形状完全一样：

| 我核了什么（便宜、且都是对的） | 我没核什么（承重） | 后果 |
|---|---|---|
| `0x100196960` 六条指令的原始字节；它落空到 `0x100196964` | **那个 sink 提交的是不是池引用** | 真正的池 sink 在 `0x100197470`/`0x100197488`，且**受同一道倒计时门控**。判决反了 |
| F82 的 RED **打印**出来了；「行消失」路径**会还原**队列 | 「快照不可读」路径的**队列内容** | 它不还原 ⇒ `owed=0` ⇒ 欠账永久消失。RED 是装饰 |
| agy 交付的 16 条控制**全 PASS**，两条抽查归因正确 | 剩下 14 条**测的是什么** | 后续 pass 挖出 `WORK` 逃逸、`MEMO` 从 `$HOME` 解析、未知参数被 `shift` 吞掉 |

⚠️ 注意第三行：我**抽查**了两条，这在统计上是合理的做法，
**但控制脚本不是随机样本** —— 交付方知道哪几条最可能被抽查。

## 1. 核验前必须先回答的那一个问题

**不要先核对任何东西。先回答：这份结论如果是错的，最可能错在哪一条?**

写下那一条，然后**第一个就核它**。如果它核不了（要几小时构建、要真机、要重新反汇编一千条指令），
那就**如实写「未核验」**，不要用外围那几条的通过去替它背书。

判别一条主张是否承重，问：**如果只有这一条是假的，结论还成立吗?**
答案是「不成立」的那一条就是承重的。通常只有一到两条。

当天两次翻车，如果我先问这句，都能避免：

- F69 的承重条是「`0x100196960` 是不是那个 sink」，不是「那六个字节对不对」。
  字节对不对我一条 `otool` 就能看；sink 唯一性要枚举整个函数。**我核了前者，报了后者。**
- F82 的承重条是「RED 之后队列里还剩什么」，不是「RED 有没有打印」。
  两者都只要一条 `cat`。**我连便宜的那条都没想到问**，因为我把「打印了」默认当成了「处理了」。

## 2. 七条已被实测打穿的推理捷径

每一条都带日期与读数，所以它们是可复核的，不是格言。
⚠️ 按 CLAUDE.md 的保鲜期规则，引用任何一条前先自己重跑那条命令。

### 2.1 用比例推出来的数，不能当判据

| 我推的 | 真值 | 倍数 |
|---|---|---|
| `$13.36 / M eq`（从消费面板的总额除总量） | `$5.43`（会话自己的成本报告） | 2.5× |
| `2.11%/h ↔ 2.05M eq/h`（拿一个点标定） | 差分两个额度读数得 `0.188%/h` | 2.9× |
| 「47% 的命令数 ≈ 47% 的时间」 | 实测占 **61.6%** 的 edge-work | 方向相反 |
| 「干净重建装不进一轮」 | **569 秒**，冷构建模型上限 ~18–20 分钟 | 装得进 |
| 「`ninja -n \| grep -c .` 永远不可能是 0」 | `--quiet` 下**就是 0**，且有 93 个真待办时也是 0 | 假的 |

**共同点：每一个都是靠比例/推理得出，而不是量了两个点作差。**
⇒ **规则：一个要当判据用的数，必须来自两个带日期的观测之差；靠缩放得到的数只能当数量级指示。**

⚠️ 还有一个方向性事实值得单记：**前两次锚错都把常量推向「更紧」**
（`COOLDOWN` 推到 21600、差点劝停 1 小时冷却）。这不是随机误差，是有方向的偏差。

### 2.2 「它报了」不等于「它处理了」

- F82：`RED` 打印 + 队列留空 + `owed=0` + 无警告 ⇒ **它宣告了它自己完成的那次丢失。**
- `.loop/RESCUED`：label 写对了、索引偏一位 ⇒ 照它看的是另一个 stash 的 diff。
- `agy -p`：`rc=0`、输出 307 字节，内容是 `no output produced — read_file permission auto-denied`。

⇒ **规则：对每一个红，问的不是「它打印了吗」，而是「下一个读者看到的系统是什么状态」。**
红之后如果计数归零、文件留空、笔记指错，那这个红是装饰。

### 2.3 一整套全绿的控制，可信度来自它红过

当天我两次误读同一件事：agy 的控制 harness **全部报 `EXPECT=0`**。
第一次我判定这是「判据不可能失败」的签名 —— **误报**，它报的是自己的断言而非被审对象的 rc，
而被审对象**故意不用 rc 发信号**（`rc=0` 在那套代码里是常量）。
第二次我因此放松了，**漏掉了那条 RED 留空队列的真缺陷**。

⇒ **规则：在信任一套控制之前，先亲手让它红一次。** 没见过它红，就等于没见过它工作。
⇒ **推论：`rc` 是常量的系统里，控制必须断言「打印了哪一行」，而不是退出码。**

### 2.4 承重的负控制必须走「被测的那个机制」

F69 第一版 flip 测试：把 `ldr w24,[x22]` 改成跳转 —— **删掉的是分类路径,不是耗尽预算**。
它证明了仪器不恒定，**没证明仪器在读预算**。
换成按我要求的更强 flip（改预算初始化为 0 / 极大）后：**判决不变** ⇒ 那份追踪是恒等式。

⇒ **规则：负控制要沿着「被审主张所声称的那条因果」扰动。**
沿着别的路径把它弄红，只证明它不是常量。

### 2.5 归因到「哪一道闸门红了」，不是「退出码变了」

同一天我自己犯了一次：给 `cards_check.sh` 加列形状检查后，七个扰动全 `rc=1`，我记成「控制通过」。
但把 `state` 改坏会**同时**触发 check 1（memo 集合不一致）—— `rc=1` 分辨不出是哪一道响的。
重做后逐条归因，check 5 确实被点名（`F900(state=bogus)`），结论才站住。

⇒ **规则：一次红必须能说出是哪一条判据、点名了哪一个对象。**「rc 变了」不是归因。

### 2.6 我在修某个缺陷时，最容易犯的就是那个缺陷

- 修 F65（审查脚本不许从环境取被审对象）时，我的守卫读的是
  `[ -n "${GAP_EVIDENCE:-}" ]` —— **而脚本自己在上面赋过这个变量**。我读的是被审对象写的值。
- 修 F82（队列消失必须报红）时，我的红**让队列保持为空**。
- 抓到这两次的都不是复核，是「未扰动必须保持绿」和敌意 pass。

⇒ **规则：修完一个缺陷，把那个缺陷的判别法套到自己的补丁上跑一遍。**

### 2.7 我的测量装置自己会坏，而它坏的时候看起来像被测对象坏了

2026-09-16 一天之内**七次**。这一类比 §0 那条更高频，因为它没有任何症状 ——
读数看起来完全正常，只是指向错误的结论。

| 我看到的 | 我差点得出的结论 | 真因 |
|---|---|---|
| `gap_evidence_check.sh` 在副本目录跑 → `rc=2` | 「我的守卫引入了回归」 | `$HERE` 指向副本，数据文件不在 |
| `structural_evidence_check.sh` 同上 → `rc=1` | 同上 | 同上 |
| 伪造 `HOME` 后 `rc=0` | 「第 ② 项没修好」 | **`rc=0` 才是正确行为**，我把期望写反了 |
| `patch -p0`（照交付说明）→ `Reversed ... detected` | 「这份 diff 是坏的」 | diff 里是绝对路径，`-p0` 命中了作者自己已改好的副本 |
| 其后三个 `/post` 控制报 FAIL | 「补丁有缺陷」 | 是我上一步污染了它的 fixture 目录 |
| `grep -E '^---'` 的输出看着折了行 | 「diff 头畸形」 | 显示层压缩，**文件字节是好的** |
| `pgrep -f run_round.sh` 命中 | 「有轮次在跑」 | 它也匹配冷却期的 tick，白等十分钟 |
| `grep -oE 'CONTROL [a-z0-9_-]+'` 零命中 | 「它没按要求的格式输出」 | 格式串是 `CONTROL %s`，漏的是我的正则 |

**共同点：全部是「装置的设置」错了，而不是「被测对象」错了。**
而每一次的读数都长得像一个真缺陷 —— 这正是它危险的地方：
§0 那一类至少让人心里没底，这一类让人**确信**。

⇒ **规则：先用同一套装置测「已知为好」的那个状态。**
如果我的装置连未改动的基线都复现不出来，它还没资格去判改动后的状态。

三条 cwd/副本错误，只要先跑一次基线就全部会暴露。
第三行那条（期望写反）要另一句才防得住：
⇒ **写下期望值时，把「为什么这个方向是对的」一起写下来。**
「`HOME` 伪造后应当**无效果**，所以 `rc=0`」——写出来就不会写成 `want != 0`。

⚠️ 还有一条判别启发式，实测有效：
**一个只有我一个人、而且是第一次测量时才出现的失败，先怀疑我的装置。**
别人的运行、CI、作者自己的运行都报正常，唯独我这次红 —— 那更可能是我，不是它。

## 3. 落成动作：读一份交付时的顺序

```
0. 先用同一套装置测【已知为好】的那个状态（§2.7）。复现不出基线，就还没资格判改动后的状态
1. 先写下「如果它错，最可能错在哪一条」——不看结论，先写这个
2. 第一个核那一条。核不了就写「未核验」，不许用别的通过去替它背书
3. 找出交付里所有【数】，逐个问：它是量出来的，还是推出来的？
   推出来的一律降级为数量级指示
4. 亲手让它的控制红一次（选一条我自己挑的扰动，不是它写的那条）
5. 对每个红，读一遍红之后的系统状态：计数、文件内容、下一个读者会看到什么
6. 归因：说出是哪一道判据、点名了哪个对象。rc 不算
7. 把被修缺陷的判别法，套回补丁自己身上
8. 把每一条【我没核的】写进卡片/提交信息，不要留在脑子里
9. 写期望值时，把【为什么这个方向是对的】一起写下来（§2.7 第三行就是漏了这句）
```

第 8 条是最容易省掉的一条，而省掉它的代价是：**下一个读者会以为整份都核过了。**

## 4. 委派的分工：破坏可以外包，建设不行

2026-09-16 的 16 次委派给出一个够清楚的分界（agy/gemini-3.8-flash-high 与本地 Opus subagent 各 8 次）：

```
破坏性（证伪 pass）   16/16 全部有实质产出，0 次走过场
                      而且四次打中的是【我自己】报出去的结论
建设性（出补丁）      4 次里 3 次「结构对，但承重那一处有缺陷」
                      F65 一致性 · F82 自己前提上 fail-open · F78 期望值观测侧写死
```

**缺陷位置高度一致：永远落在「让判据能够失败」的那一部分。** 这是可预测的，不是随机的。

⇒ **分工规则**
- **证伪 pass 放手外包**，包括交给更便宜的模型。它稳。
- **实现可以外包，但「判据能不能失败」这一关必须由我驱动一条它没写的控制。**
  实测：4 个补丁里 3 个的阻断性缺陷，是越过它自己的绿控制才发现的 —— 它的控制一条都没报。
- **只读输出不算检查。** 读输出那一版会把三个缺陷全部放行。

## 5. 账面本身的问题：卡片数不是进度

当天净账：关掉 2 张（F70、F75），新开或退回 6 张（F80、F81、F82、F83、F69 退两次、F65 将退）。

**这不是坏消息** —— 那些卡本来就是债，只是原先不可见。
但它说明一件事：**「卡片清零」不是这个阶段的终点。**

阶段判据是对拍矩阵的 `unknown`，而那个数 **2026-09-11 至 09-16 一格没动，始终是 24**。
当天推进 `unknown` 的只有 F55（`UNEXPLAINED 39425 → 23320`），其余 15 次委派都在还债和修工具。

⇒ **规则：每张卡都要声明它能不能动 `unknown`。** 大多数不能，这没问题 ——
但必须**可见**，否则「今天关了三张卡」会被读成「今天推进了阶段」。

## 6. 我自己的协调原语是备忘，不是机制

同日三例，都是我说了但没有任何东西强制的约束：

- `COOLDOWN` 的临时抬高，靠提交信息里一句 `RESTORE TO 3600`。**我差点忘了。**
- 两个派发器共用三棵工作树，唯一的协调原语是**人去改一个常量**。
  状态词表有 `open/built/closed`，**没有一个词表示「有人正在做」**。
- 「有轮次在跑」我用 `pgrep -f run_round.sh` 判 —— **它会匹配冷却期的 tick**，白等了十分钟。
  真判据是「有 `round start` 而没有配对的 `round end`」或看锁文件。

⇒ **规则：一条我用散文写下的约束，要么变成机制，要么明确标注「未强制」。**
标注了至少不会有人以为它被执行着。
