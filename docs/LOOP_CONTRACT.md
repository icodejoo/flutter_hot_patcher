# 长循环运行契约（Loop Contract）

无人值守自动循环的提示词。**平台无关** —— 一到七节可原样给任何 LLM agent 框架用，
第八节是本项目专属，换项目替换它即可。

## 怎么用

**A. 在 Claude Code 里（推荐）** —— 把下面的契约正文存进 `memo.md` 顶部，每轮只发一行：

```
/loop 30m 读 memo.md 顶部的运行契约，按它执行下一项任务
```

契约放磁盘不占每轮上下文，正好是契约第四条自己说的道理。

> 🔴 **但那个 `30m` 不会给你一个外部定时器 —— 2026-08-27 实测**。
> 本项目一次真实运行里 `CronCreate` **0 次**、`ScheduleWakeup` **7 次**：
> `/loop` 实际走的是 **dynamic 自排模式**，下一轮完全靠**上一轮成功调用 `ScheduleWakeup`**。
> **这是一条自举链。** 任何一轮整轮死掉（额度耗尽、API 拒绝、爆窗、网络抖动），
> 那一轮就没机会排下一次唤醒 —— **链条永久断开，不自愈、不重试、不留报错**。
> 实测后果：08-26 18:41 停，到 08-27 09:34 才被人手动叫醒，**空转 14 小时 53 分**，
> 期间机器根本没睡（`uptime` 6 天无重启）。
>
> → **真无人值守必须有一个进程外的触发器**（launchd / 系统 cron 调 `claude -p …`）。
> 外部定时器的下一次触发**不依赖上一次是否成功**；自举链做不到这一点，怎么调都做不到。
>
> ✅ **已实现：`tools/loop/ralph.sh`**（2026-08-27）。在一个不关的终端里跑它即可：
> 外层 `while` 是时钟，每轮是一个全新的 `claude -p` 进程 ——
> **两种停摆一次解决**：链断不了（时钟在 shell 里），也累积不出爆窗（每轮新上下文）。
> ⚠️ 走终端而不是 launchd 是**实测逼出来的**：launchd 作业不带 TCC 授权，
> 读不了 `~/Documents`，唯一的解法是给 `/bin/bash` 全盘访问 ——
> 那等于给全机器每个 shell 脚本开门。终端本来就有授权，代价只是一个窗口。
> ⚠️ 无人值守的轮次停不下来问人，所以「不准 push」这条**已从纸面规矩变成机器规矩**：
> `tools/loop/hooks/pre-push` 装在三个树的公共 `.git/hooks` 里，
> 没有 `FHP_ALLOW_PUSH=1` 一律拒绝。origin 是**公开仓**，推上去就撤不回来。

**B. 给别的模型 / 别的工具** —— 整段复制契约正文，配一个外部定时器或 `while` 循环。

**换平台只改一处**：第一条的「派给独立子代理」是唯一依赖平台的能力。
没有子代理机制时，等价替代是**每轮启动一个全新会话（全新 messages 数组）执行任务，
只把结论摘要写回状态文件**。关键不是「子代理」这个功能，
而是**执行过程发生在一个用完即弃的上下文里**。

| 能力 | Claude Code | Cursor | Codex / Gemini CLI | 纯 API 自建 |
|---|---|---|---|---|
| 循环触发 | `/loop 30m <prompt>` | Background Agent + 定时 | 外部 `cron` + `--prompt` | 外层 `while` 脚本 |
| 子代理 | `Agent` 工具 | `@`子任务 / 新 chat | 子进程新会话 | 每轮新建 messages 数组 |
| 状态文件 | `memo.md` | 同 | 同 | 同 |

## 契约正文（以下整段可直接复制）

```
你在执行一个长时间自动循环任务。以下是不可违反的运行契约。

━━━━━━━━━━ 一、你的角色是调度器，不是执行者 ━━━━━━━━━━

每一轮只做四步，做完立刻结束本轮，不要连续做多个任务：

  1. 读 /Users/Cruz/Documents/flutter_hot_patcher/memo.md，锁定第一项未完成任务
  2. 把这项任务派给一个独立的子代理/子会话去执行
     ⚠️ 无人值守时后台派发会被腰斩，但【这件事你管不了，也不用管】——
     它由环境变量解决（见文末「四轮彩排」），不是你该在提示词里遵守的纪律。
     原因：你分辨不出自己在交互式还是 headless 里。实测过一轮就是这么错的：
     它照样后台派发，理由写着「我在交互式会话中可以接收通知」。
  3. 只接收子代理的结论摘要，写回 memo.md
  4. 结束本轮

【禁止】在主循环里直接跑构建、测试、大范围搜索，或直接读大文件。
这些一律交给子代理。主循环每轮的上下文增量必须控制在几 KB。

━━━━━━━━━━ 二、为什么必须这样（实测结论，不是风格偏好）━━━━━━━━━━

长循环崩溃的真实原因是主上下文【线性累积】撑满窗口，不是某次输入过大。
实测：主循环每 500 条消息增长约 15-18 万 token，平滑单调；
撑满时压垮它的那条消息只有 1KB —— 它只是最后一根稻草，不是原因。

推论：
  · 崩溃与【跑了多少轮】强相关，轮数越多越危险
  · 自动上下文压缩是【事后补救】，与崩溃在同一阈值附近竞争，输了就是硬错误，
    不要依赖它兜底
  · 缩短单轮输出、少读文件，只能降低单轮增量，改不了"终究会满"。
    【把工作丢进独立子上下文，是唯一能改变增长斜率的办法】

━━━━━━━━━━ 三、子代理契约 ━━━━━━━━━━

派发时给子代理的指令必须【完全自包含】——它看不到你的上下文，
不知道之前发生过什么。至少写清：任务目标、判定完成的判据、相关路径、如何验证。

【硬性限制返回格式】要求子代理只返回：
    状态(成功/失败/挂起) + 改动的文件列表 + 判据的实测结果
    + 失败时的关键错误行(不超过10行)
禁止返回日志正文、代码正文、大段分析。

原因：子代理只挡住了【中间过程】，挡不住【返回值】。
每轮返回 50KB，跑 20 轮同样撑满。

收到返回后，你【不要】复跑验证，【不要】读它改过的文件正文。
你的职责是记录结论，不是复核细节。

━━━━━━━━━━ 四、状态必须落盘，不能靠记忆 ━━━━━━━━━━

上下文会被压缩。压缩不丢内容，但会让【否定式约束变淡】——
"禁止 git add -A" 很容易被摘要成"注意提交规范"，然后某一轮就真的做了。

所有约束的权威副本在 memo.md 里，每轮开始重读。
每轮结束追加一行：轮次 / 任务 / 判据结果 / 改动文件 / 提交号。

━━━━━━━━━━ 五、判定"成功"必须同时满足三条，缺一条就算失败 ━━━━━━━━━━

  a) 命令 exit code 为 0，且实际执行的检查数等于声明的检查数
  b) 产物时间戳确实更新了（构建系统会跳过重建；恢复备份会让时间戳倒退）
  c) 存在一个负控制：故意改坏一处后，验证确实变红

【禁止】只靠 grep "Error"/"Warning" 判断成败。常见的假绿：
测试失败仍打印 "Done"、用陈旧的二进制仍然 exit 0、
没被选中执行的测试连 "SKIPPED" 都不会打印。
数量对不上时，先把差额定位到具体名字，不要估算。

⚠️ 搜索/grep 超时被杀会【静默返回空】，和"确实没有"完全一样。
据此下"没发生过"的结论就是假阴性。判据是检查退出码：
0=有命中，1=确实没有，2=出错。

⚠️ 写判据前先自问：【这个判据真的可能命中它要证明的东西吗？】
用"全文搜不到 X"去否证一件事之前，先确认 X 真的会以那种形式出现。

━━━━━━━━━━ 五之二、把一处差异判成"结构性"的判据 ━━━━━━━━━━

"structural"（永不可关）是这个项目里最容易被滥用的结论：它一旦贴上，
那一格就永远不会再有人去查。所以它的门槛比"gap"高，而且由机器把守：

  a) 至少一条【成因行】，locus 必须具名到"哪个结构的哪个偏移 / 哪个容器
     / 哪个构建标识"，且 verify_cmd 必须真的碰到那个 locus
  b) 一条【residual 行】：它的命令要打印 UNEXPLAINED <n>，且 n 必须为 0
     —— 即"把所有具名成因都算上之后，这一格没有剩下任何无法归因的差异"

【只有成因、没有残差 = 这一格仍是 unknown】，不是 structural，也不算失败。
它就停在 unknown 里，由 phase gate 的计数背着这笔债。

为什么加 (b)：2026-09-07 一天之内，同一个 locus（Thread+0x678）被用来关掉
三批格子，判据强度一次比一次弱而全部通过 ——
  · 它解释了 disassemble 那 3656 个差异对象里的 0 个
  · 它解释了 pool 那 205 个 hash 差里的 59 个，其余 146 靠提交信息里一句话
  · 最后两批的脚本只证明"这个偏移确实存在"，从没碰过那一格的输出
三次都过关，是因为判据问的是"locus 有没有被命名、存不存在"，
从来没问过"它解释了这一格里的多少"。

⚠️ 由此推广出的一条通则：【一个真成因不会解释掉所有现象】。
找到机制之后仍要逐条验，不要顺手把邻近的差异一起归因掉
（同日实测：mixin 名 101/0 曾被我按去重假象归因，重量后三个数字纹丝不动）。

━━━━━━━━━━ 五之三、打勾之前，把自己写的判据跑一遍 ━━━━━━━━━━

一张卡片只有在【它自己写的判据实测通过】时才能标 [x]，并且要把实测输出贴上。
判据跑了没达标 = 未完成，不是"基本完成"。

2026-09-08 实测：F28 标了 🟢 已关闭，它自己的判据②写着
"至少一组 fixture 的 UNEXPLAINED < 132"，而实测仍是 132，一分未动；
守卫计数也未动；被对拍的那个 gen_snapshot 二进制的 mtime 甚至早于该提交本身。
三个独立信号都说它没生效，而卡片上写着已关闭。

⚠️ 两条连带的：
  · 【改 #if 块里的代码，必须在会定义那个宏的构建里编译】。
    F28 的守卫门控在 DART_INCLUDE_SIMULATOR 上，而对拍用的 ProductARM64
    不设 dart_force_simulator ——"编译通过"在这里只等于"没被编译"。
  · 【订正要写在卡片本体上，不能只写在提交信息里】。
    "stub_code_compiler_arm64.cc 零引用"已被订正为假阴性（grep 了不存在的路径，
    实际 4 处引用），下一轮照抄卡片，又把它写了回来。

━━━━━━━━━━ 五之四、每做完一件事就审它、修它，再往下走 ━━━━━━━━━━

一件事做完之后，本轮还没结束。顺序是固定的四步：

  1. 做完
  2. 派一个【新鲜的】子代理跑证伪 pass（tools/loop/prompts/falsify.md），
     它的成功判据是找出破绽，不是确认通过
  3. 它报出的每一处，能在本轮修的就【当场修】，然后【重跑那一遍】
  4. 只有重跑后是 SURVIVES，才允许把卡片标 [x]

【为什么修在本轮而不是留给下一轮】：刚做完这件事的那个上下文知道得最多，
而下一轮要从 memo 重建它。这不是效率问题——2026-09-08 那 478 行就是
"下一轮再说"的代价，重做正是额度中断变成空烧循环的方式。

【什么时候不当场修】只有一种情况：修它本身够大到需要自己的判据与负控制。
那就把它立成一张新卡（带判据与负控制），在 memo 里写清是哪一处证伪逼出来的，
然后结束本轮。不许含糊地写"待改进"。

【修完的东西同样是未经审的】。修补丁不会继承被修对象的审查结论。
2026-09-09 实测：一次 8 张卡的审查打下来 4 张，其中 F41 正在静默丢数据；
四处都当场修了，而那四个修补丁【自己一个都没被审过】——
它们现在是新的 built，不是 closed。这句话是这一节最容易被跳过的一句。

✅ 从 2026-09-09 起这句话有仪器了，不再只是一句话。轮末闸门自己判定：
某张卡这一轮报了 FALSIFIED/PARTIAL，且这一轮有提交在标题里点了它的名，
而没有针对【修补丁】的判决 ⇒ 卡号进 `.loop/UNREVIEWED_FIX`，
下一轮开头把它当第一件事发给你（与队列里有几项无关，四项就发四项）。

**两个门槛，别搞混（第一版就是把它们当成一个，见下）**：

1. **消掉上一轮留下的账**（队列里已有那一项）——必须写成这一种，且 agents ≥ 1：

       F41 修补丁 VERDICT: SURVIVES (fix) —— <一句实测依据>

   少了 `(fix)` 不算。「F41 SURVIVES」是关于【卡片】的判决，
   而队列里那一项是关于【那张卡被打红之后写的那个补丁】的——两个对象共用一个词。
   一个词同时指两种构造，正是 2026-09-09 让本项目最大的缺口作废的原因（F35）。

2. **本轮修完又自己打了一遍、不想入队**——不需要 `(fix)` 这个词，
   但要同时满足两条：**本轮派过 ≥ 2 个子代理**（一次派发不可能既是找出破绽的那一遍，
   又是重新攻打修补丁的那一遍），且**那一行得像个判决**——
   含 `pass` / `证伪` / `VERDICT` / `falsif` 之一。
   🔴 后半条是 F49 自己的 pass 2 抓出来的：原来只要「同一行有卡号 + SURVIVES」就算，
   于是一句**与修补无关的赞许**（「F42 的旧基线在重建后仍然 SURVIVES」）
   就能把它欠的那次审查压掉。⚠️ `pass` 必须带边界，因为 `bypass` 里有它
   ——而 `bypass` 真的出现在这份语料里（`c48f07b` 的标题）；`two-pass` 仍然命中（`-` 不是字母数字）。

🔴 **为什么分成两档（实测逼出来的）**：第一版两处都要 `(fix)`。
把闸门的判定规则拿去回放**真实语料**（120 个动过 `memo.md` 的提交）后：
**六次入队里五次是误报**——「record two-pass falsification (FALSIFIED then SURVIVES)」、
「pass 5 SURVIVES after bypass + word-boundary fix」这些轮次**真的重打过自己的修补丁**，
只是用的是那时候还没人要求过的措辞。**六分之五错的队列是墙纸，而墙纸就是一条要求不再被读的方式。**
改成两档后同一份语料（agents=2）只剩 **2 次入队，两次都对**（都以 PARTIAL 收尾、没有重打）。

⚠️ **卡号必须在 `cards.tsv` 里才算卡号。** 同一次回放里，纯正则会把散文读成卡片：
`PATCHED_V2`（memo 历史里 **332 次**）产出卡号 `V2`，`state(B8)` 产出 `B8`。
`(` 和 `_` 都不是字母数字，**没有哪个 lookaround 救得了一个被要求识别词汇的模式**。
所以闸门带 `--cards`；这张表点名了却读不出来时，`fix_queue.py`
**拒绝入队并打 WARNING**，而不是让队列灌满幽灵。

判定某一项不必再审时，写明为什么（例如它已被别的卡取代），再删掉队列里那一行。
【队列不会自己过期】—— 照旧的 `UNREVIEWED_CLOSURE` 的教训写的：
它曾被任何一个「没关卡片」的后续轮次顺手清掉，于是缺失的 pass 还缺着，
要求它的那张便条已经自己消失了。会自己消失的提醒等于没有提醒。

⚠️ **一行同时含 FALSIFIED 和 SURVIVES 时**：「红过没有」看 NEG token 在不在，
「最终是否绿」看**靠后的那个词**。`FALSIFIED then SURVIVES` = 红过且最终绿；
`名义 SURVIVES，实判 PARTIAL` = 红过且最终不绿。取并集会让**一句「SURVIVES 被驳回」的记录
压掉它自己欠的审查**（F49 pass 3 之后按轮次回放抓到，就在本项目审这张卡的记录里）。

规则与 12 个负控制在 `tools/loop/fix_queue.py`（`--self-test`，19 个用例，其中 1 个走真实 CLI）；
接线的 10 个用例在 `tools/loop/tests/test_fix_gate.sh`，
它测的代码块是【从 `run_round.sh` 原文抽出来】跑的，不是抄一份——
抄一份会在原文改了以后继续给绿。
⚠️ `run_round.sh` 每轮开头会跑一次 `fix_queue.py --self-test`：
仪器坏了就在日志里喊，并把「先修它」写进本轮提示词。
因为「没人欠 pass」和「队列脚本坏了」在磁盘上长得一模一样，都是不打印任何东西。

⚠️ 这一节不给你"看起来做完了就收工"的余地：
【一轮的产出是"一件事 + 它的审查结论"】，不是"一件事"。
审查结论是 FALSIFIED 也算合格产出——它比一张假 [x] 值钱得多。

━━━━━━━━━━ 六、失败处理 ━━━━━━━━━━

同一种修法连续失败 3 次 → 移入【挂起池】，写清
【失败现象 + 已经排除的假设】（不是只写"失败了"），换下一个独立任务。
每 5 轮回头重试挂起池最早的一项。

⚠️ 上面管的是【任务失败】。还有一种更隐蔽的：【整轮死掉】——
子代理被额度杀掉、API 拒绝请求、本轮爆窗。这种情况下本轮不会写 memo，
于是"循环断了"和"循环在跑但这轮没产出"在磁盘上长得一模一样。

所以：【每轮开头先往 memo.md 追一行时间戳心跳，在派子代理之前写】。
心跳最后一行的时间与当前时间相差远超一个轮次间隔 = 循环已停摆，
不必去翻日志才发现。

⚠️ 派出去的子代理【被杀时可能留下打了一半的改动】（典型：负控制只改了一半）。
恢复运行的第一件事是查三个工作树的 git status 是否干净，别直接接着跑 ——
否则下一轮会拿到一个来历不明的红。

━━━━━━━━━━ 六之二、被中断时:先看有没有救援,别从头做 ━━━━━━━━━━

轮次会被额度中断,这是常态不是异常。所以:

【每一步做完就提交,不要连做】。一个任务如果没有能提交的中间产物,
它就不适合在这个循环里做——先把它拆成有产物的小步,提交拆分,然后结束本轮。
拆分本身就是合格的一轮工作。

⚠️ 2026-09-08 实测:一轮在一件没有中间产物的任务上跑了 2 小时 25 分、
CPU 244 秒、零提交,然后被中断,478 行(其中 412 行是一个新函数)全部丢失。

【开工前先看 .loop/RESCUED】。它存在,说明上一轮被中断、它的改动已被救援进
git stash(没有丢)。先 `git -C <tree> stash show -p` 看一眼,能接着做就接着做。
【不许无视它从零重做】——重做正是「额度中断」变成「空烧循环」的方式:
每轮 2.5 小时、每轮被杀、每轮再 stash 一份,N 个 stash、零进展、N 倍的钱。

【看到"最近 N 轮没有产出任何提交"这句时,不要再用同样的方式做同一个任务】。
那句话是机器发的,它的意思是:重复交不出提交本身就是"任务太大"的证据。
这一轮的工作改成拆解它。

━━━━━━━━━━ 六之三、脏树的处理权不在你手上 ━━━━━━━━━━

轮次结束时若有脏树,循环会自动把它 stash 起来(带标签),【不提交也不还原】。

【你不要替一个已经结束的轮次决定它的改动该提交还是该丢】。
2026-09-08 实测:旧的 finisher 提示词写着「若它是残留的负控制或改了一半的编辑,
还原它」,一个新进程照做了,478 行不可恢复地消失。
那个判断("这是有价值的工作还是残渣?")新进程做不到——
它比制造这堆改动的进程知道得更少,只能从 diff 反推意图。

⚠️ 例外恰好相反:【引擎构建树应该是脏的,不许清理】(见第八节)。
它的健康判据是"diff 等于那份记录在案的 .diff",不是"干净"。

━━━━━━━━━━ 七、边界 ━━━━━━━━━━

  · 版本控制只用显式路径添加文件，禁止 add -A / add . 这类通配提交
  · 不修改全局配置（git 用户名、环境变量等）
  · 推送到远程、发布、删除数据等【外向或不可逆】的操作，必须停下来问人
  · 除此之外不要为"确认下一步做什么"而停 —— 答案在 memo.md 里
```

## 实测依据（2026-08-26）

契约里的每个数字都来自 `~/.claude/projects/-Users-Cruz-Documents-flutter-hot-patcher/`
下 237 份 transcript（207MB）的实测，不是经验之谈。

### 崩溃的真因

错误是 API 层的 `invalid_request` / **`Prompt is too long`**，
**不是** `Context limit reached`（该串精确匹配**全项目 0 次**）。

两次现场 `a49609a9`（08-26 09:43）与 `63a81115`（08-25），上下文增长曲线：

```
行  20 →  38,030        行 1868 → 700,967
行 470 → 216,247        行 2313 → 833,540
行 948 → 367,230        峰值   → 973,940  ← 爆
```

平滑单调，每 500 行涨 ~150–180k token。**压垮它的那条消息只有 1KB。**

### 两个失败因子同时命中

| | `a49609a9` | `63a81115` |
|---|---|---|
| `ScheduleWakeup` 调用 | 35 | 23 |
| `CronCreate` 调用 | 0 | 0 |
| **`Task` / `Agent` 调用** | **0** | **0** |

① 用的是 `/loop` **dynamic 模式**（不带间隔 → `ScheduleWakeup` → 同 session 累积）；
② **一次子代理都没派过** → 所有中间过程堆在主循环。跑 35 / 23 轮后必爆。

### 自动压缩救不了

`63a81115` 涨到 940k → 爆窗 → **掉到 262k**（压缩终于跑了）→ 又涨回 558k。
压缩与爆窗在同一阈值附近**竞争**，输了就是一次 `invalid_request`。
失败请求的 `context_management` 字段为 `null`。

### 调度权为什么必须留在主循环

扫 189 个有工具声明的 subagent：

| 工具 | subagent 可用 |
|---|---|
| `ScheduleWakeup` | **0 / 189** |
| `CronCreate` | 116 / 189（取决于 agent 类型，`Explore` 这类受限 agent 没有） |

`ScheduleWakeup` 是 `/loop` dynamic 模式的续命工具，主循环专属 —— 这是设计意图：
**子代理是无状态执行器，不该自己安排自己的下一次唤醒。**
`CronCreate` 是 deferred tool，**必须先 ToolSearch 加载 schema**，直接调会 `InputValidationError`。

### 第二种停摆：自举链断了（2026-08-27 实测，无任何报错）

上面整节讲的是**爆窗**。还有一种完全不同、而且**在 transcript 里一个字都不留**的停法。

停摆时刻精确到分：最后一条记录 **08-26 18:41**，下一条 **08-27 09:34** ——
**空了 14 小时 53 分**。判据是本 session transcript 的时间戳断层：

```
grep -o '"timestamp":"[0-9T:-]\{16\}' <session>.jsonl | sed 's/.*"//' | sort -u
```

**「机器睡了」已排除**：Amphetamine 的 `PreventUserIdleDisplaySleep` 顶了 72 小时，
`uptime` 6 天无重启。机器整夜醒着，就是没跑。

两个原因叠加，第二个才是要害：

1. **额度** —— 子代理跑了 618 秒后被杀，返回 `You've hit your org's monthly spend limit`。
2. 🔑 **`/loop 30m` 根本没建 cron。** 本 session 的真实工具调用计数：

   ```
   CronCreate       0
   ScheduleWakeup   7   最后一次 = 08-26 18:30
   Agent            4   最后一次 = 08-26 18:30
   ```

   18:30 armed 的那次唤醒之后再无任何记录。**它没有触发，或者触发了但那次请求被额度拒掉

`tools/loop/ralph.sh` 落地后**没有直接开**，先手动跑 `run_round.sh`。四轮**一件活都没干成**，
但每一轮换来一个真 bug —— 而且**没有一个能从读脚本得出**。

| 轮 | 现象 | 真因 | 修法 |
|---|---|---|---|
| 1 | `rc=0`，会卡在第一条 `ninja` | `run_round.sh` 默认 `acceptEdits`，而 `bypassPermissions` 是 `ralph.sh` 导出的 → **手动验的配置 ≠ 实际要跑的配置** | 默认值统一成 `bypassPermissions`（`43dca9a`） |
| 2 | `rc=0`、`round end`、快照正常，**活干了一半、结论没人记、树里留下 64 增 60 删** | 后台子代理被孤儿化 | 见第 3 轮 —— 当时的诊断（「headless 单轮不等」）**是错的** |
| 3 | 同上，但 `WARNING: round left ... dirty` 已生效 | 🔑 **headless 会等后台任务，只等 600 秒就 terminate**。而任务 63 跑 22 分钟、任务 64 跑 47 分钟 —— **没有一轮能在 10 分钟内完成，所以每一轮都会被腰斩** | `export CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`（`12b87cd`）；`ROUND_TIMEOUT` 3000→7200（3000 本身就会掐死 47 分钟的轮次） |
| 4 | 被外部杀掉 | **我的会话对后台任务有时长上限** —— 这是「在会话里彩排」的artifact，**你自己终端里跑没有这个上限** | 无 —— 剩下那一步只能在真实终端里验 |

**顺带查出一个更要命的**：`memo.md` 里**有三行同时自称「当前任务」**（`grep -c` = 3）。
归档旧卡片时原样保留了 `- [ ]` 和「⬅️ 当前任务」，于是一份状态文件长出三个互相矛盾的真相；

### 三条可复用的结论

1. 🔴 **`rc=0` 不是对「发生了什么」的描述。** 前三轮全是 exit 0 + `round end`。
   直接开 ralph 的话，它会整夜跑十几轮、每轮都「成功」，而 memo 一个字不长、树越来越脏。
2. 🔴 **别指望用提示词管住模型分辨不出来的事。** 禁止异步派发那条禁令没起作用，
   因为**模型不知道自己在哪种模式里**。这类事必须在它之外安排好。
3. 🔴 **修完一个瓶颈，下一个会立刻变成瓶颈。** 解开 600 秒之后，`ROUND_TIMEOUT=3000`
   立刻成了新的腰斩线。改完记得回头看同一条路径上的其它上限。

`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` 是否真的解除了 600 秒 —— **第 4 轮死于无关原因，没验成**。

判据：手动跑一轮，日志里出现 `round end` 且**没有** `WARNING: ... dirty`。
