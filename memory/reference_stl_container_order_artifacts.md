复刻 Shorebird 私有 dump 时，若出现「行集合/多重集合完全相等，但逐字节不同」，
**第一怀疑对象是他们把行塞进了 `std::unordered_map` 而不是 `vector`**，文件顺序就是
容器的迭代顺序，不是任何算法的产物。

`--print_dd_function_identity_to` 就是这样解掉的（2026-08-24，commit `10bc4f54b6d`，
七个 fixture 全部 `cmp` 相同）。libc++ `__hash_table` 的两条性质决定了形状：

- 插入**空桶**时节点被压到唯一那条侵入式链表的**头部** → 从不碰撞的键最终**倒序**输出；
- `__do_rehash` 只搬「新桶已被占用」的节点，其余保持原位 → 曾经碰撞过的键**永远黏在一起**。

桶宽序列 **2, 5, 11, 23, 47, 97, 197, 397, 797, 1597**（不小于 2 倍前值的最小素数）。
尾部每一个短 run 都是某个桶宽下的碰撞：键 47..48 在宽 47 时撞、97..103 在 97、
197..204 在 197、397..409 在 397、797..825 在 797。

**识别信号**：尾部出现「常数差」配对（当时记的是差 797），且该常数**跨不同大小的程序保持不变**。
常数不随程序规模变化 ⇒ 它是容器宽度，不是数据属性。

**三步验证（从便宜到贵）**：

1. Python 里照抄 libc++ 的 insert/rehash 规则，喂升序键，比对他们的顺序；
2. 12 行 C++ 直接用真的 `std::unordered_map<intptr_t,int>` 打印迭代顺序 —— 这一步把
   「我重推了他们的算法」和「这就是容器本身的行为」区分开；
3. 改我们的 `gen_snapshot`，`cmp` 全部 fixture。

**实现铁律：绝不能 `reserve()`。** 桶宽历史就是顺序，reserve 会直接跳到终宽。

**⚠️ 反例（2026-08-24 当天就证伪）**：`print_field_table_link_info_to` 症状看着一模一样
（字节数相同、多重集合相同、371/622 行错位），**但不是这个原因**。四条假设全否：
容器迭代序（组内置换约 50% 升序步，没有前插/碰撞聚簇的痕迹）、逆序、类表顺序、owner cid。
真正的线索是：**97/97 个含多字段的 owner class，两边的类内字段顺序完全一致**，只有类之间的
交错不同，且两边各自跨运行确定。这就是**堆遍历顺序**差异——属于 CLAUDE.md 已归档的
「本质上要求两个 VM 完全一致」那三类，是完成度的*度量*，不是可单独攻克的任务。

**所以判据要收紧**：光看「集合相同、字节不同」不够。要看置换**有没有结构**——
容器 artifact 会留下「长递减跑 + 常数偏移的短跑」；堆序差异是结构性随机、
但会**保住局部（同一分配簇）的相对顺序**。先做这个廉价判别，再决定要不要深挖。
